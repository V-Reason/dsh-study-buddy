# 文档式笔记规范（2026-10 重构）

**笔记就是文档块**：一个块 = 一个**可独立阅读的知识单元**，落成 vault 里一篇普通 `.md`（带 frontmatter 与 ID），与旧笔记同库同目录。

**写法没有模板**：结构、详略、文风、公式与图表偏好、领域侧重，全部由用户 vault 根的 **《笔记期望.md》** 决定。代码里没有内建模板，技能里也不定义小节清单——**你要做的是读期望并照着写**。

正式笔记不受对话的快速/详细模式影响。对话模式只决定本轮讲解深度，笔记始终要完整、可独立阅读。

## 可读性生成顺序

默认采用“问题中心的引导式工作样例”，但这不是固定小节模板：

1. 先给一个可观察的问题、故障或具体数字，说明机制为什么必须存在。
2. 在依赖它的类型名、字段和代码出现前，解释所有载重概念。
3. 交代对象、时机、输入和输出，再推进一个关键状态变化。
4. 用主图或数字 trace 展示变化，再放与当前子目标对应的真实实现。
5. 保留失效边界、验证方法和可复用工程索引。

“教学主线＋工程索引”是默认组织方式：正文前半段负责让读者重新建立心智模型，文末或对应阶段保留源码地图、测试、诊断和实现细节。不要把工程细节删光，也不要把开头的理解路径替换成字段清单。

## 课程笔记锚点

由课程母图生成的笔记，在导语后加入 `<!-- course-anchor -->` 和四项实际值：

```text
<!-- course-anchor -->
- 运行链：R2
- 课程位置：R2.3 输入缓冲
- 上一输出：采样器已留下按下沿
- 本步输出：缓冲中保留有效时刻
```

`course-anchor` 是 lint 规则：标记存在但四项缺失或为空时硬错误。锚点只负责把笔记接回课程因果链，不替代正文的问题、对象、trace、源码和边界。

## 文风与表达形式

- 默认采用克制技术散文。段落直接承载事实、机制、证据和边界；删除讲者旁白、重复收口、空泛评价和装饰性比喻。
- 技术信息完整性优先，但不靠重复和铺陈证明“完整”。只保留推进理解所必需的解释、例子和过渡。
- 正文先建立“为什么需要它”的问题主线，再按因果进入概念、状态变化和实现。结构可以按内容变化，但前一段必须为后一段留下未解决的问题，不能按文件名或字段清单平铺。
- 优先保留资料中的精确术语、有效例子和原有表达；不无差别保留讲解过程、面试口播和会话互动。
- 讲解与笔记均可使用 Mermaid；笔记中渲染失败才回退为紧凑 ASCII。按关系选择形式：线性因果用箭头链或编号步骤，层级与依赖用 `flowchart`，类关系用 `classDiagram`，数据结构用 `erDiagram`，交互时序用 `sequenceDiagram`，状态迁移用 `stateDiagram-v2`，版本与事件顺序用 `timeline`，多对象共同维度用表格。
- 分类使用缩进树，设计取舍使用共同维度矩阵，排障使用“触发 → 症状 → 根因 → 修复”链。图只在关系本身复杂时使用。
- 笔记包含生命周期、多方交互或跨时刻状态变化时，至少有一张主图。每篇只设一张主图，其他细节用代码、表格或短段落。不能把所有关系都默认画成 `flowchart`：时序用 `sequenceDiagram`，状态用 `stateDiagram-v2`，长时间顺序用 `timeline`，依赖和分支才用 `flowchart`。一张图必须替代至少三四句本来要写的话，或揭示文字不易看出的边界；否则删图。
- 图必须承载结构信息。简单定义和单点事实直接写正文；图旁只解释关键边、触发条件、失效点和判断依据。删除主图后会失去关键顺序或边界，才说明这张图值得保留。
- 每篇只有一个 H1，正文从 H1 开始，后接一段普通导语。引用块只用于外部原文，不作为标题前的重复摘要。
- H2 表示主要论证阶段，H3 表示其内部机制；不设固定小节模板。加粗只标记术语、关键条件或真实风险。
- 第一屏先给问题与结论；载重概念定义完成后，再给对象关系、状态 trace 和适用边界。一段一个观点，同一段出现两条以上并行因果链时改为图、差异表或编号步骤。
- 课程笔记的第一段先说明本篇在哪个运行链、从什么输出接到什么输出；没有课程锚点时不要伪装成课程正文。
- 前置、后续和关联集中放在文末。正文不默认附加“90 秒口径”、面试问答或总结表，除非用户明确要求。

## 工程笔记质量闸

本文件是工程笔记最低质量要求的唯一执行来源。对话讲解的最小证据规则不用于压缩正式笔记；正式工程笔记以“以后不回源码也能理解、借鉴和验证”为完成标准。

**没有模板不等于没有最低内容要求。** 不规定固定小节和标题名，但工程机制笔记落盘前必须具备：

- 一个可观察的根问题或失败场景，说明该机制为什么必须存在。
- 所有载重概念都在首次使用前得到定义；尤其不能先出现依赖该概念的类型名、字段名或代码块，再让读者自己补“这是什么”。
- 对象所有权与生命周期：谁创建、谁持有、谁调用、谁释放。
- 触发时机与入口：在哪个生命周期、帧、事件或外部操作下开始。
- 可定位源码：仓库相对路径与符号名，例如 `Assets/Scripts/.../Root.cs · Assemble()`。
- 核心调用链或状态流：输入、关键分支、状态变化和输出；至少有一个真实输入的状态 trace，让读者看见数据或控制流如何变形。
- 足以复现机制的代码或数据契约切片，不整段搬运实现。
- 至少一条失效边界和一条可执行验证路径。
- 证据级别：源码已核对、测试已覆盖、运行已观察、待验证；没有实际执行的验证不得写成已观察结论。
- 适用与不适用条件，以及可以迁移或不应照搬的边界。

写前先按上述项目整理知识清单，并把结论映射到源码符号、测试或运行证据。代码注释只能作为线索，不能直接替代对行为的核对。若关键项适用但尚未查清，继续核对源码，不进入 `note_write`。

`note_lint` 只检查可机械判定的数据卫生与结构信号，不能证明概念顺序、因果链和解释完整。语义复查至少要回答：删掉源码后，能否只读正文说清“为什么需要、关键概念是什么、输入怎样变化成输出、何时失效、怎样验证”。

纯决策、需求或复盘总览可以没有核心代码切片，但仍须说明范围、判断依据和证据状态；若源码地图不适用，在正文用一句话说明原因。

每篇工程机制笔记使用 `note_write(dryRun)` 预检。硬 error 必须修复；源码地图、证据级、主图预算等 warning 默认补齐或说明不适用，不能静默忽略。预检通过后再正式落盘，并检查实际写入返回的 warning。

源码路径由 `lint.engineeringPaths` 和 `lint.sourceRoots` 参与机器校验。一个主题需要状态机和跨对象时序共同解释时拆篇互链，每篇仍只设一张主图。

## 可发现性维护

用户明确说“笔记体检”时调用 `note_library(action=audit, path=…)`；全库必须由用户明确同意后传 `path='.'`。修复前列出目标文件与字段，确认后只改元数据、微目录和明确 wikilink。元数据修复使用 `note_update(action=metadata)`，正文逐字不变。

**三条硬门禁（工具会拒绝，别试探）**

1. **未读期望不写**：归档前必须 `note_expect_get`；用户中途改了期望 → 签名变化 → 必须重读。
2. **未确认规划不写**：先 `note_plan` 出提案（**只在对话里，不落盘**），用户拍板后调 `note_plan({ action: 'confirm', rootPath: planId })` 确认；确认才置位凭据，未确认的 `note_write` 必被拒。
3. **越界路径不写**：落盘路径必须在规划根之下、标题在规划清单内、同一规划内一个标题只能写一次。

## 块的定义与拆分口径

- **一个块 = 一个能独立读懂的知识点/决策/结论**。判据不是字数，而是"单独拿出来读，读者是否需要先看别的块才懂"。
- **拒绝伪拆分**：不要把一个连贯推导机械切成多个文件；也不要让一个块塞进三个互不相关的主题。
- 篇幅由信息完备性决定：保留足以独立复读的机制、证据、失败模式和边界；删除不推进理解的铺陈。长短都不是目标。
- 主题变大就拆块，并用 wikilink 互链（`note_link`）。
- 载重术语首次出现时先给一句人话定义和当前作用，再进入依赖它的代码；重要公式与定理保留推导步骤；抽象概念配简例；易混概念按共同维度对照。
- 算法笔记包含问题重述与不变量、小输入的状态/路径图或 trace、正确性、复杂度、边界和代码；排障笔记包含可见症状、最小复现、证据、根因、修复与回归验证。

## 归档流程（触发词：整理笔记 / 生成笔记 / 归档）

```
1. study_progress(get)                    未答追问未清 → 先提示，不进入归档
2. note_library(check)                    看库状态与期望是否已读
3. note_expect_get                        读《笔记期望.md》（门禁开门；改了就要重读）
4. note_list（可多次）                     勘探现有目录层级，判断哪些目录可复用
5. note_plan                              出提案（目录结构 + 块清单 + 顺序），呈现给用户
   └─ 用户改结构 → 直接再提案一次（旧 planId 作废）
   └─ 用户拍板   → note_plan({ action: 'confirm', rootPath: planId }) 确认凭据
6. note_write × N                         逐个落块（dryRun 可先看将写入什么）
7. note_link                              建块间或跨主题关联
8. note_toc                               为每个新增/变化的主题目录生成或刷新微目录
9. note_overview                          回报覆盖情况与缺口
10. study_progress(set) + study_memory(set lastSummary=…)
```

归档通常只重组已讲内容；用户明确要求“百科化 / 工程复用 / 避免回源码”时，允许为补齐实现索引、接口契约、测试与诊断而回读源码。新增内容必须能由当前源码、测试或实际运行核实，不能借扩充笔记引入未经证实的结论。

`note_write`、`note_update(append/replace)` 已内置写前预检。工具返回 lint error 时先修内容；不要绕过工具直写 Markdown，也不要把 warning 误报成写入失败。

## 目录层级与命名

- 层级：`资料 / 章 / 节 / 块`（课程笔记四层）。项目类笔记可以少一层（`主题 / 块`）。
- **章可以是目录，也可以是一个 `第N章 …` 文件**——按用户 vault 的既有习惯来，`note_list` 先看清楚。
- **文件名不加序号前缀**：阅读顺序由 frontmatter `顺序` 键与微目录承担。
- 每个主题目录都应有 `微目录.md`：`note_toc` 只重写 `<!-- note_toc:begin -->` 与 `<!-- note_toc:end -->` 之间的生成段，用户手写的导读原样保留。生成段会导航已有的直接子主题微目录；只有子目录的容器目录也可以生成。
- 改名用 `note_rename`（同步 frontmatter 标题 + 文件名 + 全库 wikilink + 断链检测）；不要手动搬文件，那会留下断链。

## 关联（wikilink）

- `note_link`：`kind=prev`（前置）/ `next`（后续）/ `sibling`（同主题兄弟），两侧都写，落盘为 Obsidian wikilink。
- 落盘形态：`### 关联` 小节里 `- 前置：[[目标标题]]`；已存在的关联不重复添加。
- 旧笔记（无 ID 的 `.md`）默认只写笔记侧；旧笔记 ↔ 旧笔记默认拒绝，改用 Obsidian `[[]]` 内链。
- 提到旧笔记时标 `（详见笔记：<根>/<相对路径>）`。

## 增量更新（正文不留历史块）

| 情形 | 动作 | 结果 |
| :-- | :-- | :-- |
| 补充，不推翻旧结论 | `note_update(append)`（可 `section` 指定小节） | 追加进正文，**不产生版本块** |
| 推翻 / 大改 | `note_update(replace)` | **旧正文先存入 `.study/archive/`**，正文只留新版 |
| 只改一句话定位 | `note_update(definition)` | 字段级微调，不算知识更新 |
| 挪目录 | `note_update(move)` | 迁到 targetPath（同改名要重跑 `note_toc`） |
| 只修元数据 | `note_update(metadata)` | 只改来源章节/状态；正文逐字不变，原文先存档 |
| 回退 | `note_history(list/read)` → `note_restore` | 恢复前当前版本也会先存档，可来回 |

**决定权在用户**：先说清"旧 vs 新"，用户确认后再动手。

## 存量资产

- **存量卡**（有 ID、缺 `来源章节`）：可检索、可读取；补上 `来源章节` 即升级为块（`note_update(replace)` 时带上即可），会被 `note_overview` 计入覆盖度。
- **旧笔记**（无 ID）：默认只读，不自动改写。用户明确说"把这篇升级成笔记"时才 `note_update(replace)` 原地重写。
- 已存在的自由格式笔记**不批量返工**：`note_lint` 只报数据卫生问题（会话残留 / 未标语言的代码块 / 外部资源），不再有模板与分数。

## 覆盖度口径（note_overview）

- 按 `来源章节` 聚合成「资料 → 章 → 节」。语法：`《资料名》第N章 章标题 / N.N节`（无节号也合法；全角数字与多余空格会被归一）。
- **不虚构章节**：完整性只由笔记里真实出现过的章节号构成；缺口只给"未归类"与"节号跳号"提示。
- 解析不出 `来源章节` 的条目进"未归类"，补齐后即计入。

## 落盘位置

领域 → 目录映射（`presets/study.patch.yml` 里 `study` 行的 `domainFolders`）在本轮之后**只是快捷方式**：正常路径下目录来自用户确认的文件夹规划（`note_plan` 的 `path`）；未给 path 时才回退到领域键，仍未映射则落 `未分类/<领域>/`。

## frontmatter 契约

```yaml
---
ID: 202610241230_ab12cd          # note_write 自动生成，手改会被视为新对象
标题: 高斯消元法
领域: #计算方法-线性方程组        # 首个标签 = 领域键（可选）
来源: 《计算方法》                # 资料名（必填）
状态: 已确认                      # 草稿 / 已确认 / 需更新
来源章节: 《计算方法》第2章 线性方程组数值解法 / 2.1节
顺序: 3                           # 同目录阅读顺序（微目录排序用）
简介: 用初等行变换把系数矩阵化为上三角，再回代求解。
```

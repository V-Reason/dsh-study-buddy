## 二、BUG-001：期望读取状态被 ctime 变化误判为「未读」

- **状态**：已修复
- **发现路径**：新会话开场 `note_expect_get` → `note_library(action=check)`
- **影响面**：`note_library(check)` 的期望状态行；所有依赖「已读期望」的写入门禁（`note_write`、`note_update`、`note_plan` 等）
- **特征**：正文与内容完全没变，但工具提示「笔记期望尚未读取（或已更新），请重新读取」

### 1. 现象

会话开场按门禁调用 `note_expect_get`，返回期望全文（98 行）并正常写入状态文件 `.study/session.json`。紧接着调用 `note_library(action=check)`，输出末行为：

```
⚠ 笔记期望尚未读取（或已更新）：请调用 note_expect_get 读取后再写入
```

同一会话内再调用一次 `note_expect_get`，此后 `note_library(check)` 恢复为 `- 笔记期望：已读（笔记期望.md）`。

### 2. 复现步骤

1. 新会话内调用 `note_expect_get`，确认 `.study/session.json` 出现 `expect.signature`。
2. 对 vault 根目录做一次只改元数据、不改内容的操作，让文件 ctime 变化。最直接的是改 DACL 且权限项可继承（会传播到子文件）：

   ```
   icacls <vault根> /grant <当前用户>:(OI)(CI)F
   ```

   等价操作还有：复制、改名、从备份还原、权限继承刷新。
3. 调用 `note_library(action=check)`。

**预期**：`- 笔记期望：已读（笔记期望.md）`
**实际**：`⚠ 笔记期望尚未读取（或已更新）`

### 3. 实测证据

| 时刻 | 事件 | 期望文件签名状态 |
| :-- | :-- | :-- |
| 会话开场 | `note_expect_get` 成功写入 `expect.signature` | mtime=2026-09-15，ctime=旧值，size=6161 |
| 随后 | 权限修复脚本在 vault 根加了一条可继承 ACE，传播到子文件 | ctime 变为 2026-11-03 19:47:51；**mtime 与 size 不变** |
| 之后 | `note_library(check)` 比对失败，报「尚未读取」 | `session.expect.signature` 与当前签名不一致 |
| 19:49:51 | 再次 `note_expect_get` | 写入新签名，`check` 恢复正常 |

换算签名可确认：mtime 停在 2026-09-15（期望最后一次改内容的日子），size 一直是 6161，只有 ctime 被刷新。

### 4. 根因

签名函数取 `mtimeMs|ctimeMs|size` 三项（`src/store.ts` 第 86–93 行 `signatureOf`，第 5 行与第 24 行注释同样声明该口径）：

```ts
export async function signatureOf(file: string): Promise<string | null> {
  const st = await fsp.stat(file)
  return `${st.mtimeMs}|${st.ctimeMs}|${st.size}`
}
```

ctime 是「元数据变更时间」，权限调整、复制、改名都会刷新它，与正文无关。于是：

- `markExpectRead` 写入成功 → 门禁判定依据是「当前签名 === 记录签名」；
- 任何 ACL 或元数据变化 → 当前签名变化 → 判定「期望已更新，须重读」；
- 用户看到的是「你没读过」，而实际读过了。

### 5. 修复方案

1. 签名改为 `mtimeMs|size`，或直接存正文哈希（期望文件约 6 KB，单次哈希成本可忽略，且不受时间戳类变化影响）。推荐后者：一次读文件已在内存里，`crypto.createHash('sha1')` 顺手可得。
2. 若担心旧状态文件里的签名格式不同，按「格式不认识就当作未读」处理，不要静默放行。
3. `note_library(check)` 的文案改为区分两种情形：签名不匹配时提示「期望已更新」；`expect` 记录缺失时才提示「尚未读取」。当前两者共用一句话，排障时分不清。

### 6. 验收判据

- 在 vault 根执行一次 `icacls` 权限刷新后，`note_library(check)` 仍显示「已读」。
- 真正修改《笔记期望.md》正文后，`note_library(check)` 立刻显示「已更新」。
- 新增单测：mock `stat` 返回变化的 `ctimeMs`、不变的 `mtimeMs` 与 `size`，断言读取状态仍然有效。

### 7. 修复验证

- 修复版本：v1.4.1（2026-11-03）
- 测试：`tests/dirsession.spec.ts` → `BUG-001 期望签名不受 ctime 刷新影响，只随正文变化`；`tests/noteflow.spec.ts` → `BUG-001 note_library 仅元数据变化仍为已读，正文变化提示已更新`
- 复跑结论：以 `utimes` 模拟 ACL 类元数据刷新、以 `stat` mock 模拟 ctime 变化后，`note_library(check)` 仍显示「已读」；真正改期望正文后显示「已更新」，旧三段式签名也按「已更新」处理、不放行。

## 三、BUG-002：`note_update` 的 `append` / `definition` 忽略 `dryRun` 直接落盘

- **状态**：已修复
- **发现路径**：`note_update(ref, action='append', changes=…, dryRun=true)`
- **影响面**：`note_update` 的 `append`、`definition` 两个分支（源码核对结论见下）；`replace`、`move`、`metadata` 的 dryRun 行为正常
- **特征**：返回文案不带 `[dryRun]` 前缀，回显「已更新：…」，文件实际被写入

### 1. 现象

对块笔记以 `dryRun=true` 追加一段内容，返回值为：

```
已更新：游戏开发\框架\2D 动作原型\输入缓冲：手感三件套.md（补充到末尾）

<回显的完整正文，末尾已包含追加内容>
```

调用后文件 mtime 刷新，追加内容真实存在。作为对照，同一次会话里 `action=metadata` 的 dryRun 返回 `[dryRun] 将更新元数据：…（正文不变）`，文件未被改动。

### 2. 复现步骤

1. 任取一块有正文字段的笔记（用 `note_search` 找一篇 `kind=block`）。
2. 调用 `note_update({ ref, action: 'append', changes: '测试内容', dryRun: true })`。
3. 检查文件尾部与 mtime。

**预期**：返回以 `[dryRun]` 开头的预览，文件不变。
**实际**：返回「已更新」，内容已写入，mtime 刷新。

### 3. 根因

`src/index.ts` 的 `noteUpdate` 方法里，`append` 与 `definition` 两个分支没有 `dryRun` 短路（现网第 1129–1140 行）：

```ts
if (action === 'append') {
  const result = applyNoteUpdate(raw, card.id ?? args.ref, { action: 'append', changes: args.changes, section: args.section })
  await atomicWrite(card.path, result.text)   // ← 无条件落盘
  this.invalidate()
  return `已更新：${card.rel}（补充${args.section ? `到「${args.section}」` : '到末尾'}）\n\n${result.text}`
}
if (action === 'definition') {
  const result = applyNoteUpdate(raw, card.id ?? args.ref, { action: 'definition', summary: args.summary })
  await atomicWrite(card.path, result.text)   // ← 同样无条件落盘
  this.invalidate()
  return `已更新：${card.rel}（仅替换一句话定位）\n\n${result.text}`
}
```

对照其他分支：`metadata`（1114 行）、`move`（1148 行）、`replace`（1157 行）都有 `if (args.dryRun) return '[dryRun] …'`。这两个分支属于漏写，不是设计选择。工具描述里 `dryRun` 的文案是「只预演，不落盘」，与实际行为不一致。

### 4. 影响

- 「预演」会写入真实笔记，测试或演示流程容易在正文里留下垃圾内容；
- 本次实测在《输入缓冲：手感三件套》文末留下了一行测试文字，已手工删除并核对正文恢复；
- 因为 `append` 不产生存档，误写的内容不会被 `note_history` 记录，只能人工清理。

### 5. 修复方案

1. 在 `append` 与 `definition` 分支写入前加短路：

   ```ts
   if (args.dryRun) {
     return `[dryRun] 将追加到 ${card.rel}（${args.section ? `「${args.section}」` : '文末'}；未落盘）`
   }
   ```

   `definition` 同理，返回「将替换一句话定位」。
2. 若希望预览更完整，可复用 `applyNoteUpdate` 的结果但只回显、不 `atomicWrite`。
3. 补测试：对每个 `action` 跑一遍 `dryRun`，断言文件 mtime 与内容不变——现在只有 `metadata`/`move`/`replace` 有覆盖风险，`append`/`definition` 无断言。

### 6. 验收判据

- 每个 action 的 `dryRun` 返回值都以 `[dryRun]` 开头，且调用前后文件 `mtime` 与内容逐字相同。
- 测试断言：对同一篇笔记连续两次 `append(dryRun=true)`，文件哈希不变。

### 7. 修复验证

- 修复版本：v1.4.1（2026-11-03）
- 测试：`tests/noteflow.spec.ts` → `BUG-002 append / definition dryRun 不落盘（五个 action 一致）`
- 复跑结论：对 append / definition / replace / move / metadata 五个 action 逐个跑 `dryRun=true`，返回值均以 `[dryRun]` 开头，文件正文逐字不变、mtime 不变；append 与 definition 不再落盘。

## 四、BUG-003：`definition` 只改正文首引用块，frontmatter `简介` 不同步

- **状态**：已修复
- **复现**：对任一有 `简介` 字段的块调用 `note_update({ ref, action: 'definition', summary: '新的一句话定位' })`
- **实际**：正文首个引用块被替换为新定位；frontmatter 的 `简介:` 保持旧值
- **证据**：改完后同一条 `note_search` 结果里，`简介：` 显示旧文案，`片段：` 显示新文案——同一篇笔记在同一屏呈现两份定义
- **根因**：`src/note.ts` 第 279–286 行，`definition` 分支只调用 `replaceSummaryLine(parsed.body, …)` 改写正文，未动 frontmatter；而 `src/search.ts` 第 127 行取 `parsed.meta?.summary ?? extractDefinition(body)`，**frontmatter 优先**。于是检索、索引、`note_get` 摘要都读旧的，读者看到的正文是新的
- **修复建议**：`definition` 同时重写 frontmatter `简介`（有该键才写）；或反过来让「简介」的唯一来源是正文首个引用块，frontmatter 只做镜像并在渲染时重算。两种口径选一种，不要两处并存
- **验收判据**：改完 `note_search` 的 `简介` 与 `片段` 指向同一句话

### 7. 修复验证

- 修复版本：v1.4.1（2026-11-03）
- 测试：`tests/noteflow.spec.ts` → `BUG-003 definition 同步 frontmatter 简介，note_search 摘要一致`
- 复跑结论：对新写入块执行 `definition` 后，正文首引用块与 frontmatter `简介` 同为「新定位」；`note_search` 的 `简介` 与 `片段` 都显示新文案。frontmatter 只有旧别名 `定义` 时改该行；两者都没有时保持正文回退来源。

## 五、BUG-004：`replace` 不重算简介，旧简介被前置成第二行定义

- **状态**：已修复
- **复现**：对块笔记调用 `note_update({ ref, action: 'replace', newContent: '> 新的定位\n\n## 小节…' })`，`newContent` 自带首引用块
- **实际**：正文开头出现**两行引用块**——第一行是旧简介，第二行是新正文自带的定义；frontmatter `简介` 仍是旧值
- **根因**：`src/index.ts` 第 1168 行 `summary: args.summary ?? card.definition ?? undefined`；`renderNote` 会先渲染 `> 简介` 再拼接正文，正文自带引用块时形成重复
- **修复建议**：`replace` 时优先从 `newContent` 提取首个引用块作为简介（`extractDefinition`），其次 `args.summary`，最后才回退旧值；或检测正文首行已是引用块时不再前置
- **验收判据**：`replace` 后正文首行引用块唯一，且与 frontmatter `简介` 一致

### 7. 修复验证

- 修复版本：v1.4.1（2026-11-03）
- 测试：`tests/noteflow.spec.ts` → `BUG-004 replace 以 newContent 首引用块为简介，不重复旧简介`
- 复跑结论：`newContent` 自带 `> 新定位` 时，正文只出现一行该引用块，frontmatter `简介` 同步为「新定位」，旧简介不再被前置；`note_search` 的 `简介` 也显示新值。无首引用块时仍回退 `args.summary`，最后回退旧简介。

## 六、BUG-005：`note_rename` 在文件名≠旧标题时把入链改成新标题，造成断链

- **状态**：已修复
- **复现**：
  1. 创建一篇标题与文件名不一致的块（例如标题 `链路验证：甲`、文件名 `链路验证-甲.md`；`note_write` 允许两者不同，`note_rename` 也会明确提示「文件名与旧标题不一致（历史遗留）」）
  2. `note_link` 建立关联，入链按**文件名**写入 `[[链路验证-甲]]`（正常）
  3. `note_rename` 改标题为 `链路验证：甲（改名）`，文件名保持不变
- **实际**：入链被改写为 `[[链路验证：甲（改名）]]`，但磁盘上只有 `链路验证-甲.md`；Obsidian 视角这是断链。随后 `note_unlink` 返回「无改动：关联不存在」，删不掉这条链
- **证据**：改名输出「文件名：不变…」与「[[链路验证-甲]] → [[链路验证：甲（改名）]]」两行并存；`Get-ChildItem` 确认文件名未变；`note_unlink` 从两侧分别调用都返回「无改动」
- **根因**：改名路径（`src/links.ts`）把入链文本改写为**新标题**，而连接路径（`src/index.ts` 第 1281 行 `labelOf`）用**文件名**做标签，两端口径不一致；插件自身的断链检测按标题解析，因此还报告「断链检测：无」，掩盖了 Obsidian 里的真实断链
- **修复建议**：
  1. 入链一律使用文件名（与 `labelOf` 一致）；
  2. 只改标题、不改文件名时，入链**保持不变**；
  3. 断链检测按文件名解析，不按标题
- **验收判据**：改名后全库入链仍指向真实存在的文件名；`note_unlink` 能删掉这些链接

### 7. 修复验证

- 修复版本：v1.4.1（2026-11-03）
- 测试：`tests/noteflow.spec.ts` → `BUG-005 标题≠文件名时 rename 不改入链，note_unlink 可删除`；`BUG-005 标题=文件名时 rename 同步文件名与入链`
- 复跑结论：标题 `链路验证：甲`、文件名 `链路验证-甲.md` 只改标题后，文件名不变、入链仍为 `[[链路验证-甲]]`，`note_unlink` 两侧都能删除；标题与文件名一致时仍同步改名并把入链改为新文件名，未误关整条入链同步能力。

## 七、BUG-006：`replace` 丢弃正文既有的「关联」小节

- **状态**：已修复
- **复现**：块笔记已有「### 关联」小节（含 `- 前置：[[X]]`），调用 `note_update(action='replace', newContent=…)`
- **实际**：新正文里关联小节消失；对端笔记里由 `note_link` 写入的反向链接仍在，两侧关联静默失衡
- **根因**：`replace` 以 `newContent` 整体渲染新正文，未把既有关联行并入；关联只存在正文里，不在 frontmatter，因此没有可继承的字段
- **修复建议**：`replace` 时保留旧关联小节（合并到新正文末尾），或至少在返回值里提示「原有 3 条关联未保留，请用 note_link 重连」
- **验收判据**：`replace` 后 `note_link` 建立的双向关联仍完整，或返回明确警告

### 7. 修复验证

- 修复版本：v1.4.1（2026-11-03）
- 测试：`tests/noteflow.spec.ts` → `BUG-006 replace 保留既有 关联 小节`
- 复跑结论：`replace` 后旧「关联」小节逐字保留，`note_link` 建立的双向关联仍完整；`note_unlink` 能继续删除两侧链接。`newContent` 自带「关联」小节时以新内容为准，不重复追加。

## 八、附带观察（非缺陷，供改进参考）

1. **审计噪声**：`note_library(action=audit)` 会把《笔记期望.md》正文里作为**示例**写的 `[[目标]]`、`[[目标标题]]` 统计为断链；`[[xxx.png]]` 这类图片嵌入也被算作断链。建议：审计时排除期望文件，把图片嵌入单列一类（或直接忽略非笔记扩展名）。
2. **审计规模**：全库 629 篇出 668 条问题，其中 261 条是旧笔记缺 `来源章节` 的存量问题。建议按类别给「可修复/存量/忽略」三档，避免明细被存量淹没。
3. **`study_progress(brief)` 字段空**：v1.4.0 新增的阶段、下一动作、完成判据、最近结果、并行线未写入时，brief 只回退到旧三行，输出上无法与旧版区分。文档里可注明「字段为空时的降级形态」。
4. **来源章节后缀被截断**：`note_write` 传入 `《链路验证》第1章 试运行 / 甲`，落盘后 frontmatter 变成 `《链路验证》第1章 试运行`，「/ 甲」丢失。真实笔记里 `… / M1 移动闭环` 这种后缀是保留的，说明后缀识别有白名单（疑似只认 `N.N节` 或 `M\d` 类形态）。建议文档里写清「节名该用什么写法」，或在截断时给出提示。

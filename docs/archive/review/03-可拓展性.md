# 三、可拓展性评估

> 📌 本文件是 **2026-09 首轮审查的时间点快照**（已归档）：行号、路径与结论保持当时状态，不随代码更新改写；逐条修复状态见 [`docs/审查修复记录.md`](../../审查修复记录.md) §二。
>
> 判断标准：新增一类业务需求时，需要改动的文件数、是否触碰既有逻辑、是否存在"改一处漏三处"的隐式契约。
> 总体判断：**分层方向正确**（`cardmodel` 纯文本模型 → `template` 声明式规格 → `lint` 引擎 → `tools` 薄适配 → `index` 编排），但**扩展点没有收敛**：规则、模板、领域映射、工具描述、配置字段分散在 4~6 处，新增能力仍属"低侵入"的是模板/规则本身，属"高侵入"的是领域族判定与工具层。

---

## EXT-1 新增一条 lint 规则要同时改 4 处（违反开闭原则）

- **SEVERITY**：warning
- **WHAT**：
  1. `src/lint.ts:77-92` `WEIGHTS`（权重）
  2. `src/lint.ts:59-74` `RULE_TITLES`（中文名）
  3. `src/lint.ts:142-275` `lintCard()` 里新增一个 `if (!off.has(id)) { ... }` 块
  4. `src/tools.ts:277` `rule: { type: 'string', enum: ruleIds(), ... }`（枚举自动跟随，但**描述文案** `src/tools.ts:266-269` 是手写的规则清单，必须手工同步）
  5. 若规则需要新的判定函数，还要在 `src/lintrules.ts` 加导出
- **WHY**：`WEIGHTS` 是 `RuleId` 的唯一来源（`src/lint.ts:94`），所以第 1、2 步是硬耦合；第 3 步是纯手工。漏掉第 4 步会出现"规则存在但模型看不到、也不会用"的静默能力缺失——这正是本项目历史上踩过的坑类型（见 `docs/archive/dev-experience/postmortem-2026-08-21-tools-not-registered.md`）。
- **FIX**：引入单一注册表，让"加一条规则 = 加一个数组元素"：
  ```ts
  interface Rule { id: string; title: string; weight: number; run(c: RuleCtx): { ok: boolean; findings: LintFinding[] } }
  export const RULES: Rule[] = [/* 14 条 */]
  export const ruleIds = () => RULES.map(r => r.id)
  // tools.ts 描述改为 `...按 ${RULES.length} 条规则打分：${RULES.map(r=>r.title).join('、')}`
  ```

## EXT-2 模板规格与 lint 结构检查是两套口径（新增小节要改两处）

- **SEVERITY**：warning
- **WHAT**：`src/template.ts:27-88` 用 `required/optional` 声明了小节规格（数据驱动，方向正确），但 `lintCard` 又**独立实现了一遍**结构检查：`template-sections`（`src/lint.ts:166-171` 调 `checkTemplate`）、`mainline`（`174-180`）、`reentry-point`（`192-197`）、`verify-experiment`（`199-207`）、`troubleshoot-criteria`（`209-215`）、`walkthrough`（`270-275`）。其中 `SectionSpec.mainline` 字段（`src/template.ts:21`）**定义了但没有任何地方读**。
- **WHY**：给工程型再加一个必填小节（例如「性能预算」）时：改 `template.ts` 的 `ENGINEERING_SECTIONS` 只影响 `card_create` 的警告；`card_lint` 的评分、`presets/study/skills/card-format/SKILL.md`、`tools.ts` 的 `content` 描述（`src/tools.ts:131-133`）三处都要手工补。三处不同步就产生"创建时警告、体检时不查"或"技能要求、工具不查"的错位。
- **FIX**：让 lint 从规格推导：
  ```ts
  const spec = templateSpec(input.template)
  for (const s of spec.required) if (!hasSection(sections, s.title)) finding('template-sections', ...)
  const mainlines = sections.filter(s => spec.required.some(r => r.mainline && matchesTitle(s.title, r.title)))
  ```
  `mainline` 字段即可真正生效，`template-sections` 与 `mainline` 两条规则合并为一个规格驱动检查。

## EXT-3 领域族判定硬编码在代码里，新增领域要改代码 + 重启

- **SEVERITY**：warning
- **WHAT**：`src/template.ts:107-109`：
  ```ts
  const ENGINEERING_DOMAINS = ['图形学', 'Unity', 'Shader', 'URP', '渲染']
  const ENGINEERING_TITLE_HINTS = ['接入', '配置', '参数', '坑', '实现', '源码', '变体']
  const COMPARISON_TITLE_HINTS = ['对比', '谱系', '选型', '取舍', '差异', '之争', 'vs']
  ```
  与 `domainFolders`（preset 配置，`presets/study/agent.cordis.yml:204-244`）里的领域键完全脱节。
- **WHY**：用户新增一个领域（例如「数据科学」「Rust」）时，只能改源码 + 重新构建；且 `ENGINEERING_DOMAINS` 用 `includes` 做**子串匹配**（`src/template.ts:130`），`domainText = domain + ' ' + folder`，只要目录名里含"渲染"就判工程型——一个叫「渲染数学」的理论卡也会被推断成工程型，然后被 lint 要求「验证实验 ≥3 步」。这是**规则与数据两套世界**的典型症状。
- **FIX**：把三项判定表搬进 `StudyConfig`（例如 `templateHints: { engineering: string[], comparison: string[] }`），`normalizeConfig` 透传，`inferTemplate` 从参数取；默认值保持现状，行为不变。顺带把子串匹配改为"领域键精确命中或目录族前缀命中"。

## EXT-4 `VaultStore` 是 518 行"上帝类"，新增能力只能继续加方法

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:138-655`。一个类同时持有：索引缓存（`139-141`）、路径解析（`148-181`）、全库扫描/索引重建（`184-205`）、引用解析（`207-215`）、检索（`217-234`）、创建（`236-281`）、更新（`283-292`）、关联（`294-331`）、MOC（`333-364`）、lint 编排（`367-445`）、历史块（`448-468`）、改名（`471-550`）、进度（`561-589`）、记忆（`591-654`）。`src/tools.ts` 12 个工具直接依赖这个具体类。
- **WHY**：任何新增能力（导出 Anki、卡片图谱、批量重命名、Obsidian 插件协议）都要往这个类加方法，类的依赖面继续扩大；同时工具层无法用 mock 替换存储（`tools.spec.ts:5-10` 只能用真实 `VaultStore` 构造，且注释说明"不触盘"是靠不调用方法实现的）。
- **FIX**：按能力拆接口，`VaultStore` 退化为门面：
  ```
  CardRepository（ensureIndex/resolve/read/write/rename）
  SearchService（search/snippets）
  LintService（lintCard/batch/insight）
  MemoryService（memory/progress）
  ```
  `tools.ts` 依赖这 4 个接口而非具体类；新增能力优先落在新服务里，对既有逻辑零改动。

## EXT-5 检索根的"可读/可写"策略散落在 3 处

- **SEVERITY**：nit
- **WHAT**：`SearchRoot` 只有 `{path,label}`（`src/vault.ts:92-96`）；"vault 可写、其它根只读"这一业务规则分别实现在：`src/index.ts:520-524`（rename 里判 `file.root !== 'vault'`）、`src/index.ts:298-315`（link 里判 `card.id === null && !allowNoteWrite`）、`src/index.ts:344-348`（moc 里判 `card.id === null`）。
- **WHY**：新增一类根（例如"团队共享只读库"）或新增一类写操作（例如批量打标签）时，必须记得在每处都加判断，漏一处就是**跨库误写**（写坏别人的笔记）。
- **FIX**：把策略上移到根定义：`interface SearchRoot { path: string; label: string; writable: boolean }`，`IndexedCard` 携带 `writable`，所有写路径统一走 `assertWritable(card)`。

## EXT-6 `StudyConfig` / `VaultLayout` / `normalizeConfig` 三份同构定义

- **SEVERITY**：nit
- **WHAT**：`src/index.ts:47-71`（StudyConfig）、`src/vault.ts:199-218`（VaultLayout）、`src/index.ts:82-105`（normalizeConfig 逐字段搬运），三者字段几乎一一对应；`src/vault.ts` 里 `VaultLayout` 的注释是 `StudyConfig` 注释的复制品。
- **WHY**：新增一个配置项要改 3 处（类型 ×2 + 搬运），且 `VaultLayout` 的 `lint` 字段（`src/vault.ts:214-217`）是内联结构类型，`StudyConfig.lint` 也是内联结构类型，二者已存在轻微重复；漏改 `normalizeConfig` 会出现"配置写了但插件读不到"的静默失效（历史上 `includeSessionCwd` 就有过类似语义漂移）。
- **FIX**：`VaultLayout = Omit<StudyConfig, 'vaultRoot'> & { vaultRoot: string }`，或直接 `normalizeConfig` 返回 `StudyConfig & { vaultRoot: string }` 并删除 `VaultLayout`；`lint` 抽成具名 `LintConfig` 接口。

## EXT-7 工具返回值是纯文本，没有结构化出口

- **SEVERITY**：nit
- **WHAT**：`src/tools.ts:20-23` 与 `34-35`：所有 12 个工具共用 `output = { schema: { type: 'string' }, render: renderText }`，`execute` 一律返回拼好的中文字符串。
- **WHY**：文本返回对模型友好，但**堵死了结构化消费**：将来要在 GUI 里渲染卡片预览（Slot/Tool Card）、或让 `card_lint` 结果被其他工具程序化消费（例如"只重写 score < 70 的卡"），只能重新解析人类可读文本。改造成本随工具数量线性上升（12 个）。
- **FIX**：不要求现在改；但把"每个能力返回一个 `{ text, data }` 对象"作为下一步约定——`ToolDef.execute` 返回类型放宽为 `string | { text: string; data: unknown }`，`render` 负责取 `text`，老调用方不受影响。

## EXT-8 领域键表三处同步靠人肉

- **SEVERITY**：nit
- **WHAT**：`presets/study/agent.cordis.yml:204-244`（映射）、`presets/study/skills/card-format/SKILL.md`（键名表）、`src/template.ts:107`（工程族）。`tests/skills.spec.ts:121-130` 只断言 SKILL.md 里**出现了** `图形学-动画特效` 等关键词，不校验与 YAML 键集合一致。
- **WHY**：新增/删除一个领域键后，SKILL.md 与 YAML 漂移不会被 CI 拦住；模型按 SKILL.md 写卡 → `card_create` 回显"未映射" → 落 `未分类/`，用户要重启才发现。
- **FIX**：加一条测试：解析 `agent.cordis.yml` 的 `domainFolders` 键集合，断言 SKILL.md 的键名表与之完全一致（当前已具备解析能力，`tests/skills.spec.ts` 的 `parseSkill` 可直接复用）。

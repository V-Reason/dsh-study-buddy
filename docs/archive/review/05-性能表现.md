# 五、性能表现分析

> 📌 本文件是 **2026-09 首轮审查的时间点快照**（已归档）：行号、路径与结论保持当时状态，不随代码更新改写；逐条修复状态见 [`docs/审查修复记录.md`](../审查修复记录.md) §二（复审复测见 [`07-复审-修复验收.md`](07-复审-修复验收.md) §六）。
>
> 测量环境：Windows / 本地 SSD（T: 盘）/ Node 22 / vitest 进程内计时。
> 方法：临时构造 vault 并计时（探针脚本已删除，参数与结果记录如下），全部为**单次调用**耗时，含 `refresh()` 的全库扫描。
>
> | 场景 | 规模 | 结果 |
> | --- | --- | --- |
> | A | 300 卡 × ~1KB | `search` 首次 79ms / 二次 25ms；`lint(vault)` 85ms；`lint(cross)` 81ms；`lint(trend)` 84ms；`rename` dryRun 105ms / 实写 102ms |
> | B | 1000 卡 × 4KB（约 4MB 正文） | `search` 首次 537ms / 二次 **61ms**；`get` 54ms；`lint(单卡)` 115ms；`lint(vault)` 537ms；`rename` dryRun 381ms / 实写 383ms |
>
> 结论：**本地 SSD 上单次调用 50~550ms，可接受；但"每次调用都全库扫描"的固定开销与"批量工具重复读盘/重复解析"是本轮重构放大的主要退化点。**

## PERF-1 每次工具调用都做全库 `walk + stat + 签名拼接`（无 TTL）

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:184-205` `refresh()`：`walkRoots` 递归 → 每文件 `stat`（`src/vault.ts:114-116`）→ 拼一个包含全部 `root|rel|mtime|ctime|size` 的字符串 → 与上次比较。任何工具（含 `card_get` 这种"只读一篇"）都走这条路径。
- **WHY**：实测固定开销：300 卡 **25ms**、1000 卡 **61ms**（B 场景 `search#2` 即纯签名成本）。这还只是本地 SSD：Obsidian vault 常放在 OneDrive/坚果云/网络盘，`stat` 单次可能 1~10ms，1000 文件即 **1~10 秒/次调用**；再乘上"一次归档要调 5~10 次工具"，交互会明显卡顿。
  负载阈值：**文件数 > 500 或 vault 在同步盘上**时问题凸显；单机本地 300 卡时（25ms）可接受。
- **FIX**：加两层短路，语义不变：
  1. TTL 缓存：距上次扫描 < 2000ms 直接复用 `this.index`（写操作仍显式 `this.sig = null`）；
  2. 目录级 mtime 预检：先 `stat` 各根顶层目录与一级子目录，mtime 未变且文件数一致则跳过递归（Obsidian 外部编辑会更新父目录 mtime）。
  最小改动版：只加 TTL，一行即可。

## PERF-2 批量 lint / 单卡 lint 重复读盘：索引里已有正文

- **SEVERITY**：warning
- **WHAT**：`refresh()` 已经把每篇正文存进 `IndexedCard.body`（`src/search.ts:37-38,124`），但 `VaultStore.lint()` 又对每个文件串行 `fsp.readFile`（`src/index.ts:411-423`），只为拿 `template` 字段和重新解析 frontmatter。
- **WHY**：B 场景 1000 卡 × 4KB：`lint(vault)` 537ms，其中 `refresh` 61ms、1000 次串行读盘 + 1000 次 `parseFrontmatter` + 6×1000 次 `splitSections` 占绝大部分。串行 `await` 还让磁盘 IO 无法重叠（读 1000 个 4KB 文件本可用 `Promise.all` 或 16 并发在 1/5 时间内完成）。
  负载阈值：**卡片数 > 300 或单卡 > 4KB** 时凸显；"正文长度不设上限"的设计（README `:12`）会让这个成本持续上升。
- **FIX**：
  1. `IndexedCard` 增加 `template?: string`（`indexNote` 里顺手存 `parsed.meta?.template`）；
  2. `lint` 改用 `card.body` / `card.template`，仅在需要"磁盘最新版本"时才读盘；
  3. 保留读盘兜底：若 `card.body` 为空则读文件。

## PERF-3 同一份正文被解析 6 次 + `blankOutBlocks` 3 次（每卡）

- **SEVERITY**：warning
- **WHAT**：`src/lint.ts:139` `splitSections(body)` 已经切好小节，但后续检查各自重新切：
  - `checkTemplate`（`src/template.ts:149`）、`checkMainline`（`src/lintrules.ts:240`）、`checkSelfTest`（`128`）、`checkLayers`（`167`）、`checkLinksBlock`（`223`）、`checkExperiments`（`232`）各调一次 `splitSections`；
  - `scanResidue`（`src/lintrules.ts:62`）、`bodyLength`（`src/lint.ts:193`）、`bodyLength`（`src/lint.ts:280`）各调一次 `blankOutBlocks`。
  合计 **6 次全正文正则扫描 + 3 次全正文逐行重建**，而 `lintCard` 里 `sections` 与 `bodyLength` 结果都是现成的。
- **WHY**：每次 `splitSections` 都是 `HEADING_RE.exec` 遍历全文 + 数组分配；`blankOutBlocks` 会 `split('\n')` 后 `map` 重建整串。单卡 4KB 时约 9 次全量字符串操作；1000 卡时就是 9000 次。B 场景 `lint(单卡)` 115ms 里，refresh 占 61ms，剩下 ~54ms 主要是这部分。
  负载阈值：卡片正文字数越大越明显；配合"不设字数上限"的定位，属于**会随业务增长而恶化**的结构性开销。
- **FIX**：让检查函数接受已算好的中间产物（保持纯函数）：
  ```ts
  const sections = splitSections(body)
  const residueText = blankOutBlocks(body)
  checkMainline(sections); checkSelfTest(sections); checkLayers(sections); ...
  bodyLength(residueText)   // 复用同一份 blankOut 结果
  ```
  零行为变化，预计单卡 lint 成本降 30~50%。

## PERF-4 `lineOf(index) = text.slice(0, index).split('\n').length` → 每卡 O(n·小节数)

- **SEVERITY**：nit
- **WHAT**：`src/insight.ts:48-52`（`extractFacts` 对每个 section 调 `lineOf`）、`src/history.ts:67`（`extractHistory` 同样）。
- **WHY**：每个小节都做一次"前缀切片 + split"，整卡成本 ≈ 正文长度 × 小节数；`cross=true` 对全库跑（`src/index.ts:432-435`），1000 卡 × 6 小节就是 6000 次前缀切片，且每次都分配一个新字符串。B 场景 `lint(cross)` 81ms 里可见其占比。
  负载阈值：卡数 > 500 且每卡小节 > 6 时凸显；当前规模可接受。
- **FIX**：预计算一次换行位置数组（`const nl = []; for (let i=0;i<text.length;i++) if (text[i]==='\n') nl.push(i)`），`lineOf` 改为二分查找；或直接按行遍历构造 `{line, text}`。

## PERF-5 `card_rename` 全库读 + 逐文件重写 + 逐文件断链检测

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:492-532`：`walkRoots` → 对**每个文件** `readFile` + `parseFrontmatter` + `rewriteCardLinks`（内部 `splitSections` + `renderSections`）+ 卡片再 `rewriteWikilinks` + 命中时 `detectBrokenLinks`（又一次 `splitSections`）。
- **WHY**：B 场景 1000 卡实测 **381ms（dryRun）/ 383ms（实写）**，且这是"改一个标题"的代价。若 vault 在同步盘上，1000 次读 + N 次写会更慢；`searchRoots` 只读根也会被完整读一遍（`src/index.ts:493`）。
  负载阈值：卡片数 > 500 时凸显；单次操作 0.4s 尚可接受，但它是**用户感知最强**的操作（改名后要等结果）。
- **FIX**：
  1. 先用索引里的 `titleTokens`/`fullRel` 做**预筛**：只对"可能含旧标题"的文件读盘（例如 `titleTokens`/`bodyTokens` 命中旧标题 token 的文件），可把 1000 次读降到个位数；
  2. `detectBrokenLinks` 只对"本卡改写后的正文"跑一次，而不是每个改动文件跑一次；
  3. 只读根直接跳过读盘（当前会读完再判断 `file.root !== 'vault'`）。

## PERF-6 `search` 对全部命中先算 snippet 再截断；单字 CJK 查询拉全库

- **SEVERITY**：warning
- **WHAT**：`src/search.ts:231-258`：遍历 `scores` 里**每一个**命中，构造完整 `SearchHit`（含 `snippetOf(card, tokens)`——对全文按行 `toLowerCase()` + `includes`），排序后才 `slice(0, limit)`。另外 `tokenizeQuery`（`src/search.ts:80-88`）对长度 ≤4 的 CJK 串展开单字。
- **WHEN/WHY**：查询 `你`/`的`/`光` 这类单字时，倒排表命中几乎全库，`scores` 装满 N 条，于是**全库正文都被扫描一遍算 snippet**，只为返回 5 条。1000 卡 × 4KB 时约 4MB 字符串扫描 + N 次数组分配。
  负载阈值：**单字/双字查询 + 卡片数 > 500** 时凸显（实测 `search('你')` 在 300 卡下 15ms 尚可，但这是"命中少"的巧合——`你` 在 300 张测试卡里没出现）；真实 vault 里"的/是/我"必然全库命中。
- **FIX**：先排序取 top-`limit`，**只对入选结果算 snippet**；对单字 token 降权（如权重 ×0.2）或限制单字 token 的 postings 参与上限。

## PERF-7 索引查询是线性扫描，`indexScopes` 每次搜索都全量遍历

- **SEVERITY**：nit
- **WHAT**：
  - `src/search.ts:184-191` `byId`/`byTitle` 用 `cards.find(...)`（O(n)）；`src/index.ts:338-352` `moc` 对每个 `cardIds` 调一次 → O(n·m)；
  - `src/index.ts:226-229` `indexScopes` 每次搜索 `index.all().map(c => c.root)` 建 Set，只为拼一行"来源"。
- **WHY**：B 场景下 `byId` 单次 ~1000 次比较，`moc` 传 20 个 ID 就是 2 万次；`indexScopes` 每次搜索固定 O(n) 分配。功能正确，但属于"白送的开销"，且随卡数线性增长。
- **FIX**：`rebuild()` 时建 `idIndex: Map<string, IndexedCard>`、`titleIndex: Map<string(lower), IndexedCard>`、`rootSet: Set<string>`。

## PERF-8 索引常驻全库正文（内存随库线性增长）

- **SEVERITY**：nit
- **WHAT**：`src/search.ts:37-38` `IndexedCard.body: string`，`rebuild` 时整份保留（`src/search.ts:156-168`）。
- **WHY**：1000 卡 × 4KB ≈ 4MB（可接受）；但按"正文不设字数上限"的定位，若出现 10 万卡 / 平均 8KB 的库，索引常驻约 800MB，加上倒排表与 `lint` 期间临时副本会显著吃内存。当前规模**可接受**，属于需要写进架构约束的边界。
- **FIX**：需要时改为懒加载：`IndexedCard` 只存 `path + 前 N 字符`，`snippetOf` 命中时才读文件；或对 `body` 加 LRU。

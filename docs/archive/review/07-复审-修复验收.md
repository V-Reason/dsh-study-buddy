## 五、本轮新发现（修复副作用）

### N1 `card_link` 在一侧只读时**先写后错**，留下半写盘状态

1. **SEVERITY**：warning（数据一致性，优先级最高）
2. **WHAT**：`src/index.ts:392-413`。`applySide(from,…)` 先落盘，`applySide(to,…)` 内部才 `this.assertWritable(side.card)`（`:399`）抛错。探针 P1 实测：vault 内 `A.md` 已被写入 `- 后续：\`B卡\`（202601010000_bbbbbb）`，只读根里的 `B.md` 未写，工具返回 `ERR: "other/B.md" 位于只读检索根（other）：本插件只写 vault 内的文件`。
3. **WHY**：这正是 BIZ-2 要消灭的形态——**用户看到"失败"，但数据已被改动**，且留下单向入链（A 指向 B、B 不指向 A）。触发条件现实存在：`searchRoots` 指向第二个卡片库，或 `includeSessionCwd` 的工作目录里放卡片，且默认 `linkIntoNotes: false`。修复前该路径会**静默写入只读根**（更糟），本轮加了 `assertWritable` 却没调整顺序，等于把一个"误写"换成了"半写 + 报错"。
4. **FIX**：把两侧可写性判定前置到任何写入之前（2 行）：
   ```ts
   const writableSides = [from, to].filter((s) => s.card.id !== null || allowNoteWrite)
   for (const side of writableSides) this.assertWritable(side.card)
   ```
   或复用 `rename` 的 plan→commit：先算两侧 `next` 文本与 `changed`，全部成功再 `atomicWrite`。

### N2 `card_create` 每次调用都触发全库重扫 + 重建索引

1. **SEVERITY**：warning（性能回归，热路径）
2. **WHAT**：`src/index.ts:325`（`create` 为了同名提示调 `ensureIndex`）与 `:360`（写完 `invalidate()`）互相放大：每次建卡都会让下一次建卡重建索引。1000 卡（~1KB 正文）实测 `create 冷=265ms / create2=232ms / create3=239ms`；400 卡实测 `92~128ms`。修复前 `card_create` **不碰索引**（0 额外 IO）。
3. **WHY**：建卡是最热的写路径（一次归档 3~5 张卡很常见），每条卡片都要多付一次全库 `walk + stat + readFile + tokenize`；在同步盘（OneDrive/网络盘）上会被放大到秒级。附带耦合：`ensureIndex` 的抛错（超 `MAX_WALK_FILES`、vault 瞬时不可读）会让**建卡整体失败**，而这条路径的产出只是一条"提示"。
4. **FIX（三选一，按推荐度）**：① 增量维护 `Map<lowercaseTitle, {rel,id}>`（`ensureIndex` 重建时填充，`create`/`update`/`rename` 后更新），同名检查变 O(1)；② 同名检查改为"索引新鲜才查"——`if (this.index && this.sig !== null && Date.now() - this.lastScanMs < ttl)`，冷索引时跳过提示（提示不是门禁，跳过可接受）；③ 降级为写后校验：写完再查同名并提示"可能存在同名卡片"。

### N3 索引 TTL 默认 2s 造成外部编辑可见性回归

1. **SEVERITY**：warning（业务可用性）
2. **WHAT**：`src/index.ts:242-248` 的 TTL 早退发生在 `walkRoots` 之前。探针 N 实测：扫描后立即在 vault 外部新建 `b.md`，`search('独特关键词QQQ')` **未命中**；同一序列在 `indexTtlMs: 0` 下立即可见。
3. **WHY**：修复前每次调用都重扫，外部编辑永远即时可见；现在存在 0~2s 窗口，窗口内 `card_search` 会"未命中"，`card_get`/`card_update`/`card_rename` 会"找不到卡片"。而"用户在 Obsidian 里刚写完笔记，立刻让 Agent 读/改"正是本插件的核心用法。文档已记录该边界（用户指南 :773、:719），但用户不会先读文档再踩坑。
4. **FIX**：在"未命中 / 找不到卡片"的失败路径上做一次强制重扫（cache-miss retry，最多一次），既保留 TTL 的收益又消除整类误判；或把默认 `indexTtlMs` 降到 500ms（1000 卡全扫 240ms 仍可接受）。

### N4 `addLink` 在小节无尾换行时把关联行粘到标题上

1. **SEVERITY**：warning（低概率，静默破坏结构）
2. **WHAT**：`src/card.ts:344-346`。`nl === -1`（`### 关联卡片` 是文件最后一行且无 `\n`）时 `insertAt = body.length`，实测输出 `### 关联卡片- 前置：\`乙\`（id2）`。
3. **WHY**：关联行不再是独立列表项——Obsidian 不渲染为列表、`links-format` 规则认不出它（`^[ \t]*-` 不匹配该行）、后续 `addLink` 判重也会漏判。工具仍报告"已建立关联"，属静默失败。该缺陷在修复前同样存在（非本轮引入），但 BIZ-6 恰好重写了这段逻辑，属于顺手可修。
4. **FIX**：`const insertAt = nl === -1 ? body.length : nl + 1` 之后统一补换行——`return nl === -1 ? \`${fm}${body}\n${line}${body.slice(insertAt)}\` : …`；或把 `line` 改为 `\n- ${label}：…` 并在开头按需补 `\n`。

### N5 `noteSkips()` 未覆盖 `moc()`，且跳过原因被丢弃

1. **SEVERITY**：nit
2. **WHAT**：① `src/index.ts:454` 的 `moc()` 返回值没有 `noteSkips()`，而 `docs/审查修复记录.md`（当时为审查 README）`:198` 声称"`search`/`lint`/`rename`/`moc` 追加 ⚠ 跳过 N 个文件"；② `src/index.ts:251` 的回调 `(entry) => skipped.push(entry.path)` 只留路径、丢掉 `entry.reason`，探针 J 因此把"目录深度超过 16 层"显示成"⚠ 跳过 1 个文件（读取失败/无权限）"，且计数对象其实是**目录**不是文件。
3. **WHY**：BIZ-7 的初衷是"报告数字必须与实际处理了哪些文件一致"；现在数字对上了，**原因却是错的**，会把用户引向"权限/锁定"这个错误方向。moc 的文档承诺未兑现。
4. **FIX**：`skipped` 改存 `{ path, reason }`，`noteSkips()` 按 reason 分组输出；`moc()` 补 `this.noteSkips()`（或删掉 README 里那一句）。

### N6 `MAX_WALK_FILES` 硬上限把"慢"变成"整个插件不可用"

1. **SEVERITY**：nit（大库用户是 warning）
2. **WHAT**：`src/vault.ts:159-164`，`out.length >= 20000` 直接 `throw`，异常穿透 `walkRoots → ensureIndex`，于是 `card_search`/`card_get`/`card_create`/`card_update`/`card_lint`/`card_rename` 全部失败（只有 `study_progress`/`study_memory` 可用）。上限是**每根** 2 万，且无配置可调（`MAX_WALK_FILES` 是模块常量）。
3. **WHY**：大型 Zettelkasten 超过 2 万篇并不罕见（首轮报告建议 5000 是为了拦整盘扫描，本轮取 20000 已放宽，但语义没变）。修复前这类 vault 是"能跑但慢"，现在变成"完全不可用且无法自救"。安全阀的合理语义是"拦住异常根"，而不是"拒绝正常的大库"。
4. **FIX**：加 `config.maxWalkFiles`（默认 20000）并在错误信息里指向它；或超限时改为**截断扫描 + 显式警告**（`⚠ 仅扫描前 20000 个文件，结果可能不完整`），把失败降级为可感知的降级。

### N7 `residueLevel: 'off'` 时报告仍宣称"✓ 通过：会话残留"

1. **SEVERITY**：nit
2. **WHAT**：`src/lint.ts:156`（`if (c.residueLevel === 'off') return []`）→ `:392` 的 `passed[rule.id] = out.length === 0` 把"未执行"记成"通过"。探针 F 实测 `formatReport` 输出 `✓ 通过：会话残留、…`。对比 `rulesOff` 的规则不进 `passed`、工具回显"未启用或不适用于此类文档"，两者口径不一致。
3. **WHY**：用户把残留检查关掉后，报告反而给了一个"通过"的绿灯，会让人误以为卡片已体检过该项。属于"报告说假话"的同类问题（首轮 BIZ-5 的残留）。
4. **FIX**：让 `run` 返回 `LintFinding[] | null`，`null` 表示未执行（`if (out === null) continue`），`session-residue` 在 `off` 时返回 `null`。

### N8 死代码 `sectionHints`

1. **SEVERITY**：nit
2. **WHAT**：`src/template.ts:181-183`，全仓零引用（`docs/审查修复记录.md`（当时为审查 README）`:172` 声称"`sectionHints`/`templateTable` 真正用于生成工具描述"，实际只有 `templateTable` 被 `src/tools.ts:144` 使用）。
3. **WHY**：与 CPLX-8 同类问题（导出即契约，无人调用即负债）；修复表里的这条陈述与实际不符，会让下一位维护者以为改它有效。
4. **FIX**：删除 `sectionHints`，或用于 `validateCard` 的缺节提示文案（`src/card.ts:144` 现在手拼 `### ${section.title}`）。

### N9 `rulesOff` 中的未知规则 id 静默忽略

1. **SEVERITY**：nit
2. **WHAT**：`src/lint.ts:388-392` 只做 `off.has(rule.id)` 判断，`src/index.ts:457-462` 的 `lintCtx()` 不校验 id 合法性。探针 P6：`rulesOff: ['walkthrough', 'typo-rule']` 无任何提示（`walkthrough` 恰是本轮删除的规则 id）。
3. **WHY**：用户按旧文档/旧版本配置写 `rulesOff`，规则被删除或写错时会"以为关了其实没关"，且没有任何线索。
4. **FIX**：`normalizeConfig` 用 `ruleIds()` 校验 `rulesOff`，未知 id 直接抛错（fail-loud），或至少在 lint 报告末尾列出"未识别的规则 id"。

### N10 分数分布桶标签出现 `100~109`

1. **SEVERITY**：nit
2. **WHAT**：`src/lint.ts:470`，`range: \`${lo}~${lo + SCORE_BUCKET - 1}\``。探针 E 实测满分卡片显示 `100~109 分 1 篇`。
3. **WHY**：满分区间不存在 109 分，报告数字自相矛盾；批量体检是给用户看"整体质量"的，这种小错会削弱可信度。
4. **FIX**：`range: \`${lo}~${Math.min(lo + SCORE_BUCKET - 1, 100)}\``。

### N11 文档/实现三处不一致

1. **SEVERITY**：nit
2. **WHAT**：① `docs/用户使用指南.md:482` 说"14 条规则（**全部警告级**）"，同页 `:499` 的外部资源是 `0（info）`；② 当时的审查 README（现 `docs/审查修复记录.md`）`:198` 说 moc 会追加跳过提示（代码没有，见 N5）；③ 当时的审查 README（现 `docs/审查修复记录.md`）`:172` 说 `sectionHints` 已用于工具描述（实际零引用，见 N8）。
3. **WHY**：本轮修复表本身是"后续维护者的对照表"，一旦有 3 处失真，下次验收就失去基准。文档漂移是本项目反复出现的问题（首轮 BIZ-4/CPLX-9 都是它的变体）。
4. **FIX**：逐条改文字；并把"文档里的规则数/规则名"用测试钉住——`tests/skills.spec.ts` 已有 `ruleCatalog()` 可用，加一条"SKILL.md/用户指南中的规则清单 == `RULES`"的断言即可。

### N12 `inlineText` 静默压缩标题/定义中的连续空格

1. **SEVERITY**：nit
2. **WHAT**：`src/cardmodel.ts:32-34` 的 `inlineText` 除折换行外还 `.replace(/[ \t]{2,}/g, ' ')`，被 `renderFrontmatter`/`renderCard`/`replaceCardTitle` 调用。`标题: C++  STL` 会被静默写成 `C++ STL`。
3. **WHY**：SEC-1 的原则是"非法输入 fail-loud、渲染层兜底"，但空格属于**合法输入**，静默改写与"用户定稿格式"的承诺冲突（用户看到的是自己写的标题，落到磁盘却是另一个）。影响面小（文件名清洗本来就会压空格），但属于"静默数据修改"。
4. **FIX**：`inlineText` 只折换行（`.replace(/[\r\n]+/g, ' ').trim()`），把压空格留在 `sanitizeFilename` 与定义渲染处按需调用。

### N13 SEC-3 的残余：含 `[]` 的历史文件不再同步文件名

1. **SEVERITY**：nit
2. **WHAT**：`sanitizeFilename` 现在清洗 `[`/`]`（`src/vault.ts:38`），而 `planRename`（`src/rename.ts:151-158`）用 `sanitizeFilename(oldTitle)` 与文件名比对。既存文件 `A[B].md` + 标题 `A[B]` → `expected = 'A B' ≠ 'A[B]'` → 判定"文件名与旧标题不一致（历史遗留）"，改名时**不再同步文件名**。
3. **WHY**：只影响改动前就含方括号的卡片（数量应当极少），且不会写错内容——只是"改了标题但文件名没跟着改"。属于需要记录的边界，而不是 bug。
4. **FIX**：`planRename` 比较时对 `oldBase` 也做一次同口径归一（`sanitizeFilename(oldBase) === expected`），或在该分支的 `reason` 里显式说明"文件名含已废弃字符，保留原名"。

### N14 `uniqueCardPath` 二次回退只用 ID 末 4 位

1. **SEVERITY**：nit
2. **WHAT**：`src/vault.ts:298`，`id.slice(-4)`。ID 已从 4 位 hex 改为 6 位（BIZ-11b），但文件名回退仍取末 4 位。
3. **WHY**：同名标题 + 同分钟的第三张卡才会触发第三条分支（完整 ID），实际碰撞概率极低；只是"ID 加长"这个修复没有同步到所有使用点。
4. **FIX**：改为 `id.slice(-6)` 或直接 `${base}_${id}.md`。

### N15 `card_history` 是唯一未传 `sessionCwd` 的卡片工具

1. **SEVERITY**：nit（BIZ-3 的遗漏项）
2. **WHAT**：`src/tools.ts:330` 的 `card_history` `execute` 没有 `exec` 形参、不传 `sessionCwd`，而 `card_search`/`card_get`/`card_create`/`card_update`/`card_link`/`card_moc`/`card_lint`/`card_rename` 都传了（`src/tools.ts:92,106,171,229,250,274,306,352`）。
3. **WHY**：`includeSessionCwd: true` 时，`card_search` 回显的 `工作目录/xxx.md` 在 `card_history` 上仍解析失败——BIZ-3 修好了 10 个工具、漏了第 11 个，用户会得到"有的工具认、有的不认"的不一致体验。
4. **FIX**：`execute: (args, exec) => store.history(..., { … }, { sessionCwd: sessionCwdOf(exec) })`，与其它工具对齐。

## 六、性能复测

环境：本地 SSD，正文 ~1KB/卡，`indexTtlMs` 默认 2000ms。

| 场景 | 修复前（首轮实测） | 修复后（本轮实测） | 结论 |
| --- | --- | --- | --- |
| `search` 首次（1000 卡） | 537ms（4KB 正文） | 240ms（1KB 正文） | 同量级，索引构建未变 |
| `search` 命中缓存 | 无此能力（每次全扫 61ms） | **1ms** | PERF-1 生效 |
| `lint(scope=vault)`（1000 卡） | 537ms（含逐文件读盘） | **22ms** | PERF-2/3 生效（索引已持有正文） |
| `get`（1000 卡） | 61ms（全库 stat） | **1ms** | TTL 生效 |
| `rename`（1000 卡） | 382ms（4KB 正文） | 237ms（1KB 正文） | 预筛生效 |
| **`create`（1000 卡）** | **≈0 额外 IO** | **232~265ms/次** | **N2：回归** |

结论：PERF-1~7 的收益是真实的（读路径从"每次全扫"降到毫秒级），但**写路径上新增了 `create` 的全库重建**。读多写少的会话里净收益为正；一次归档连建 5 张卡时会多付约 1 秒（1000 卡规模），在同步盘上更明显。

## 七、结论与建议修复顺序

**整体结论**：这是一次**高质量的修复轮**——三个 blocker 全部真修复（含边界与回滚路径）、修复方式针对根因、回归用例补在了正确的位置、文档同步到位。剩下的问题都是"修复的副作用"和"口径细节"，没有一条会阻止发布。

**建议顺序**（合计约半天）：

| 优先级 | 项 | 改动量 | 理由 |
| --- | --- | --- | --- |
| **P0** | N1 `link` 两侧可写性前置 | ~5 行 | 唯一的"报错但已写盘"路径，与 BIZ-2 同源 |
| **P0** | N2 `create` 同名检查不再强制重建索引 | ~10 行 | 热路径性能回归，1000 卡 235ms/次 |
| **P1** | N3 失败路径强制重扫一次 | ~10 行 | 消除"外部编辑不可见"的整类误判 |
| **P1** | N4 `addLink` 无尾换行 | ~2 行 | 静默结构破坏，顺手修 |
| **P2** | N5/N6/N7/N9/N15 | 各 2~10 行 | 报告说真话 / 大库可用性 / 配置校验 / 工具一致性 |
| **P3** | N8/N10/N11/N12/N13/N14 | 各 1~3 行 | 死代码、文案、边界记录 |

**不建议在本轮做**：EXT-4 的服务化拆分、EXT-7 的结构化返回、BIZ-12 的新增两条规则——理由（成本高、收益滞后、规则集膨胀）成立，留待下次功能扩展。

**验收建议**：把本报告 N1~N4 各补一条回归用例（N1 用 `searchRoots` 里的卡片 + `linkIntoNotes: false`；N2 用"连续两次 create 的时间/扫描次数"断言；N3 用"外部写入后立即 search"；N4 用无尾换行文本），这四条正好对应"修复副作用"这一类风险，能防止下一轮再出现同类回归。

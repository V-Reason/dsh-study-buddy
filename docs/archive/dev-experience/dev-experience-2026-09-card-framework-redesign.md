# 开发经验总结：卡片框架重设计与 P0/P1/P2 三层落地（一次会话实录）

> 背景：依据 `docs/card-format-2026-09-redesign-proposal.md` 对 dsh-study-buddy 做重设计与构建。
> 用户明确要求"先重设计大框架以适配新旧需求、留足扩展性，再一一对应三个方案顺序执行"。
> 结果：v0.5.0 → v0.8.0，工具 9 → 12，测试 136 → **209 全绿**，`pnpm run check` 通过。
> 本文只谈**过程方法论**，不重复既有文档（2026-08 四特性、2026-09 修复五轮、平台适配）已总结的内容。

## 一、这次做对的三件事

### 1. 先读真实数据，再定正则（避免整轮返工）

提案 §5.2 给的会话残留正则集，直接实现会误伤——**在写代码前先对真实 vault 只读抽样了 223 张卡**，得到：

- `L\d+` 命中 15 张，其中绝大多数是 `L0/L1/L2`（球谐带）与 `GAMES101 L15`（讲义引用）；
- `今天/明天/昨天` 大量用于口语化定义（"明天天气只由今天决定"），不是会话残留；
- `M1/M2/M3` 在真实语料里多为里程碑与数学记号，按提案默认会误报一片；
- 自测题格式已 100% 带 `→` 答案（提案里的"无答案"是历史问题，已修）。

于是把规则从"宽正则 + 事后解释"改成"窄判定 + 白名单"，并把这些口径写成单测钉住。
**成本约 3 次只读命令，收益是零返工**——这正是上一轮经验 T4（根因实证而非合理猜测）的复用。

### 2. 地基先行，让三个阶段共用一套模型

原实现 `src/card.ts` 里一个常量数组 + `includes` 校验、正文是整块字符串。
如果直接在它上面加 lint，P1 的"模板分型"和 P2 的"跨卡一致性"都会被迫再做一次字符串手术。

于是先建 7 个纯函数模块（cardmodel / template / lintrules / lint / history / rename / insight），
再抽出 `tools.ts`。**判据是"后续加规则只改一个文件"**：
- 加一条 lint 规则 → 只改 `lintrules.ts` + `lint.ts` 权重表；
- 加一种模板 → 只改 `template.ts` 注册表；
- 加一个工具 → 只改 `tools.ts`。

阶段 0 的验收方式是**行为零变化**：既有 136 项测试断言不改，全绿。

### 3. 兼容口径显式化（存量数据不返工）

真实 vault 里 `### 阶梯式解剖` 有两种写法（155 张不带后缀、69 张带"（第 1 层 → 第 4 层）"）。
若按规范标题精确匹配，69 张卡会被误判缺节。于是定义：

> 小节标题匹配 = 精确相等，**或**以规范标题开头且紧跟括号/冒号/破折号。

一条规则同时解决 5 种历史变体（`核心思想（直击）`、`阶梯式解剖（限制清单…）`），并写进单测。

## 二、踩过的坑（按浪费量排序）

### 1. 正则"成对结构"用 `matchAll` 全局匹配 → 闭栅栏被当成开栅栏

`codeFenceLanguages` 最初写成 `/(?:```|~~~)\s*(\S*)/gm` 全局匹配，
于是 ``` ```hlsl\nx\n``` ``` 被解析成 `['hlsl', '', '', '']`（开、闭、开、闭全算）。
**根因**：fenced block 是成对结构，不能用无状态全局匹配。
**修复**：改为逐行扫描 + `inFence` 翻转。单测直接断言 `['hlsl', '']`。
**复用**：凡是"开/闭成对"的语法（栅栏、`<details>`、HTML 标签），一律用状态机逐行扫，不用正则全局匹配。

### 2. 领域标签混挂判定：用"含 `-`"当子域 → `Cook-Torrance` 被误判

真实语料里补充标签大量含连字符（`Cook-Torrance`、`Blinn-Phong`）。
**修复**：改为"子域 = 含 `-` **且** 有另一个标签是它的前缀（或与已知子域键同前缀）"，
并只报"根域 + 子域同时存在"。单测覆盖 4 种组合。

### 3. 改名后的断链检测把"新标题包含旧标题"当成残留

`A` → `A 与探针` 时，`line.includes(oldTitle)` 恒为真。
**修复**：断链判定先排除"已含新标题"的行。
**教训**：字符串包含判断在"改名/替换"场景必须考虑**新旧值互为子串**的情形。

### 4. 断言没跟上格式变更 → 一轮 5 处红

`addLink` 归一为 `` `标题`（ID） `` 后，`card.spec` / `store.spec` 里 5 处断言仍按旧格式写。
**处理**：逐处改成新格式（而不是回退实现迁就断言——沿用上一轮教训"改断言而不是改实现"）。
**可复用做法**：先 grep 全仓库的格式断言点（`- 后续：`、`- 前置：`），一次性改完，再跑全量。

## 三、可复用的技巧

### T1. 权重表集中化：打分规则只在一个对象里

lint 的 14 条规则权重写在 `WEIGHTS` 一个常量对象里，规则实现、报告渲染、文档口径三处引用同一份。
改口径（如"会话残留从 10 分降到 8 分"）只改一行，测试自动跟随。

### T2. "先只读、再动代码"用于一切规则类需求

lint 规则的精度问题**无法靠推理解决**，只能靠真实语料校准。
本次流程：`只读抽样 → 定规则与白名单 → 写单测（含反例） → 再实现`。
反例单测比正例更重要——它们定义了"什么不该报"。

### T3. 批量输出必须自带"总量 + 分布 + 最低分"，否则工具不可用

`card_lint({scope:'vault'})` 若逐卡打印，223 张卡会淹掉上下文。
设计为：均分 + 分数分布 + 规则命中排序 + 最低分 N 张（默认 20，可调）。
**复用**：任何"全库/全量"类工具，默认输出必须是聚合视图，明细要显式要。

### T4. 版本号与文档计数最后统一处理

本次三个阶段共享一次文档同步：`grep -r '134 项\|201 项\|9 个工具\|≥~500 字'` 一次找全，逐文件替换。
避免每个阶段都扫一遍（上一轮 T7 的加强版）。

## 四、一句话总结

**本轮零逻辑返工**，全部浪费集中在两处正则的语义误用（成对结构、子串包含）与断言滞后。
最值钱的三条：**规则类需求先只读校准再写码、成对结构用状态机、新旧值互为子串时先排除新值**。

## 二、改代码要同步哪些文档

| 改了什么 | 必须同步 | 建议同步 |
| :-- | :-- | :-- |
| 用户可见行为 / 报错文案 / 配置键 | `用户使用指南.md`（含 §4 配置表与 §11 排障表）、`README.md` 配置表 | 验证提示词 |
| 新增/删除 lint 规则 | `lint.ts` 的 `RULES` → 工具描述自动跟随；`技术文档.md` 规则表、`用户使用指南.md` §7.7、`card-format/SKILL.md` | `设计文档.md` D14 |
| 新增工具 / 改工具 schema | `技术文档.md` §3、`用户使用指南.md` §7、`README.md` 工具一览 | `tests/tools.spec.ts` 名字集合 |
| 模板 / 小节规格 | `template.ts` → `card-format/SKILL.md`、`设计文档.md` §3 | 验证提示词第 D 项 |
| 决策推翻或新增取舍 | `设计文档.md` 决策表（新编号） | `经验文档.md` |
| 性能模型 / 缓存策略 | `技术文档.md` §7、`设计文档.md` §8 边界 | `用户使用指南.md` §12/§13 |
| 审查发现的问题 | `审查修复记录.md` §二/§三 状态表 + 回归用例列 | `经验文档.md` |
| 版本号 | `package.json` + `dsh.plugin.json`（两处必须一致）、`README.md` 更新记录、各现行文档头部版本基线 | `经验文档.md` 结果行；`tests/docs.spec.ts` 会校验头部基线 |

> 版本号是**最后一刀**：代码、测试、文档全部到位后再改，改完跑一次 `pnpm run check` 并核对两个 manifest。

## 三、三条约定

1. **口径单一来源**：同一事实只在一处定义——规则集在 `src/lint.ts` 的 `RULES`、模板规格在 `src/template.ts`、
   领域键在 `agent.cordis.yml`、卡片格式在 `card-format/SKILL.md`。文档是它的**投影**，不是第二份定义。
2. **能被解析的就不靠自觉**：领域键表、规则清单、persona 重复段落、文档里的规则数与级别，都由
   `tests/skills.spec.ts` 断言（见该文件 N11 用例）；**文档内的相对链接/锚点与头部版本基线**由
   `tests/docs.spec.ts` 断言（标题改名、版本号漏改会直接红）。文档里的数字（测试项数、工具数、规则数）改了要一起改。
3. **审查报告不改写**：`docs/archive/review/01~07` 是**时间点快照**，行号与结论保持当时状态；修了没有、为什么不修，
   回填到台账 [`审查修复记录.md`](审查修复记录.md) 的状态表（§二/§三），不要回头改报告正文。归档文档同理（见 [`archive/README.md`](archive/README.md) 的归档判据）。

## 四、维护检查清单

发布或提交前，逐条过一遍：

- [ ] `pnpm run check` 全绿（typecheck → vitest → esbuild）
- [ ] `package.json` 与 `dsh.plugin.json` 版本一致，`README.md` 更新记录已加一条
- [ ] 各现行文档头部的"版本基线"已同步
- [ ] 新增/删除的规则、工具、配置键已在 §二 对应的文档中同步
- [ ] 文档里的数字（测试项数、工具数、规则数）与实际一致
- [ ] 文档内的相对链接与锚点可跳转（标题改名后尤其注意）
- [ ] 被取代的文档已移入 `docs/archive/` 并在 `archive/README.md` 登记

# 开发经验总结：五轮体验报告修复（一次会话实录）

> 背景：依据第五次体验报告（2026-09-03，GAMES101 L21-22 收尾）落地 §4 全部 9 项建议 + 报告链条上仍开放的历史项（1~3 张卡口径、文件名引号清洗、未映射回传键列表、数学适配条目）；v0.3.0 → v0.4.0；测试 116 → **134 项**，`pnpm run check` 全绿。期间经历一次**环境事故**（node_modules 被 pnpm 重建半毁 + 沙箱钳制叠加）和一次**部署副本同步事故**（Copy-Item 目录嵌套）。本文只谈**过程方法论**，不重复上一份（2026-08）已总结过的内容。

## 一、踩过的坑（浪费点，按浪费量排序）

### 1. 版本号先行 → 触发 pnpm 重装 → node_modules 半毁 + 三次无效重试（本次最大浪费，~40 分钟 + 大量往返）
- **过程**：改 `package.json` 0.3.0 → 0.4.0 后跑 typecheck，pnpm 检测"package.json ≠ lockfile importer"→ 无 TTY 中止；`pnpm install --lockfile-only` 补好 lockfile，但再跑任何 pnpm 命令都进入"Recreating node_modules"；完整重装卡死（10 分钟高 CPU）→ kill；`--offline` 180s 无输出；`--offline --ignore-scripts` 同样挂起。期间 node_modules 已半毁（`.modules.yaml`、顶层链接、甚至 `.pnpm` 里 vitest 的 package.json 都缺失）；还花了轮次查 registry SSL（`Invoke-WebRequest` 失败）以为网络断了。
- **根因**：早前整个会话处于受限沙箱（spawn/网络被钳，vitest 启动 EPERM 在计划阶段就已预期），而 `pnpm install` 与 vitest 同源受限；文件策略切到 danger-full-access 后，同一个 `pnpm install` **755ms 完成**——挂起全是沙箱，与项目无半点关系。
- **教训（三条，均为零成本纪律）**：
  1. **版本号是"最后一刀"**：代码/测试全绿之后再 bump（bump 会触发 pnpm 依赖状态检查，掉进"重装判定"）。本次顺序错误，把验证窗口和重装窗口叠在一起。
  2. **沙箱命令先探路**：流程中需要"spawn/网络"的命令（install、vitest、git push）在动手前先跑一次确认可用性；不可用就先做纯文本改动（文档/技能/报告），把跑命令的活集中到权限放开后的一个窗口。
  3. **同一命令失败后先诊断再重试**：`--offline` 连试两次属于纯浪费；正确顺序 = kill 挂起进程 → 只读诊断（store 是否完整、`.pnpm` 目录还缺什么）→ 定位根因（沙箱）→ 等权限放开一次重装。

### 2. TS 对象键带连字符没加引号 → 整个 spec 文件 transform 失败（一次全量跑 + 一轮定位）
- 过程：`domainFolders: { 图形学-动画特效: '...' }` —— YAML 合法，**TS/JS 必须加引号**。vitest 输出"110 passed + 1 failed suite"，读尾巴容易误判为"只差这一个文件"；实际整文件 PARSE_ERROR，该文件 24 个用例一个没跑。
- **教训**：中文/连字符/数字开头的对象键一律加引号（写测试时极易沿用 YAML 习惯）；全量跑出现 failed suite 时**往前翻报错头**（Parse/Transform 错误），不要被 passed 汇总迷惑。

### 3. Copy-Item 同步目录 → 目录套目录嵌套副本（Card-format/card-format/SKILL.md ×3）
- 过程：`Copy-Item "$repo\skills\*" "$dep\skills\" -Recurse -Force` 对"目标目录已存在"的条目会**再套一层同名目录**（3/6 中招，另 3 个却 merge 成功——行为不一致到令人困惑）；靠 `Get-ChildItem -Recurse -Filter SKILL.md` 数文件才发现。若直接重启 DSH，技能发现会撞出重复 skill name。
- **教训**：**同步目录用逐文件 Copy-Item（文件→文件）或 robocopy /MIR**；同步后必须做**树结构校验**（列全部 SKILL.md 路径、检查嵌套层），内容 hash 相同不等于结构正确。

### 4. 验证脚本一处 PowerShell 语法错误 → 把"操作已成功"误读为"校验失败"
- 过程：最后一条校验 `Get-Content ... -Raw -Encoding UTF8 -match ...` 把 `-match` 挂在了 Get-Content 的参数上（`-match` 只能用于表达式），脚本 exit 1；而前面所有写操作其实全部成功。
- **教训**：长 PowerShell 事务脚本**拆成"写"与"验"两段**跑，或每步打独立的 `Write-Output` 标记 + 校验用表达式写法 `(Get-Content -Raw) -match '...'`；看 exit code 前先分清"哪一步失败"。

### 5. 先设计后查证：card_id 的坑说明文档里早就存在（一轮小浪费）
- 过程：方案里为 `card_id` 设计了"文档化方案"，后来读 `用户使用指南 7.2` 才发现 08-23 postmortem 早就写了"create 不消费预取值"的坑与正确姿势（只是工具描述没同步）。
- **教训**：改 API 行为/描述前**先 grep 文档与该域 postmortem 的既有坑说明**——那都是上一轮执行者花 token 买来的经验，先抄作业再动手。

### 6. 计数文案是"全局易漏项"（多轮 grep）
- 过程："96 项测试"在 README ×4、用户指南 ×5、**历史快照文档** ×1；replace_all 会把历史快照（"当时 96→116"）也改了——历史文档保真，应手工豁免。
- **教训**：规则/计数类文案先 grep 全集 → 分文件决策 → 再 replace；"当时的事实"不随现状改写。

### 7. 小项：报告归档路径含空格（"Experience Report"）
- 每次命令都要显式引号；非本质问题，但**归档目录名含空格**会持续增加引用成本——若重来，目录名用 `experience-reports/` 这类无空格命名。

## 二、值得推崇的技巧（后续项目直接复用）

### T1. 纯函数优先 + 一次成型（逻辑返工 = 0 轮）
本轮全部新逻辑（`todayLocal`/`stripMocDatePrefix`/`validateDefinition`/`findProgressSentences`/`findSimilarDomainKeys`/引号清洗/`definition` 分支）都写成无 IO 纯函数，24 个新用例**一次全绿**（唯一失败是语法笔误，不是逻辑错误）。纯函数可独立构造输入、规则显式、测试零成本。
- **复用**：任何"行为变更"先写纯函数层（判定/渲染/清洗规则显式化），接线层薄而防御（继续沿用 2026-08 的 T1）。

### T2. 工作区外写操作 = 唯一锚点校验 + 备份 + 一次授权
对部署副本（%DSH_HOME%）与 vault 记忆/状态文件这类**用户真实数据**：
1. dry-run（只读）统计每个替换锚点出现次数必须 = 1；
2. 写脚本里再 `ReplaceOnce`（≠1 即 abort）；
3. 写前备份（`memory.json.bak-2026-09-03`）；
4. 校验输出读回 JSON/文本确认 20 键未丢、vaultRoot 未动。
本轮数据修复零风险、零回滚。
- **复用**：凡动"别人家数据"一律先备份；锚点唯一性校验让"改错位置"变成不可能。

### T3. 权限窗口合并：一次授权干完所有工作区外操作
部署副本 persona 编辑 + 6 技能同步 + vault 进度句标注**放同一个提升命令**里完成，用户只看到一次授权提示（而非 3 次打断）；随后才做只读核对。
- **复用**：盘点所有"需要权限"的动作，合并成单一批处理；授权是稀缺资源。

### T4. 根因实证而非合理猜测
- MOC 日期差一天：用 vault 实际文件名（`2026-09-01_知识目录_UnityShader第18章PBR.md` 是 09-02 会话产物）佐证 UTC 根因，而不是停留在"可能时区问题"；
- 键名表：从**部署副本**抄真实键，而不是先信任仓库 preset（仓库版本是过时的一版）。
- **复用**：bug 修复前先找磁盘/运行态证据固定根因；配置类事实以"实际生效的那个文件"为准。

### T5. 报告 = 需求源 → 执行记录 → 归档，一条审计链
原报告追加"## 5. 修复执行记录"（逐条对照 §4 + 明确边界/未修项），再移动到 `archive/`；活动目录只留未执行报告，历史不删除。未来任何一次修复都能从这里追溯"为什么这样修、哪些没修、为什么没修"。
- **复用**：体验/复盘报告不要"读完即弃"；执行后回写结论再归档，形成可检索闭环。

### T6. 回归保护 = 关键词钉住 + 一次全量
skills.spec 新增 4 条断言钉住本次关键资产：定义"≤60 字硬上限/允许放行"、键名表"图形学-动画特效"、domain-adaptation"数学/数值分析/数值稳定性"、file-reading"import pymupdf/单次调用页数上限/get_toc"。未来有人"优化"技能时立刻红。
- **复用**：凡是"提示词资产"（技能/persona），用 3~5 条关键词断言钉住，成本≈0。

### T7. 四处同步先 grep 全集
本次工具描述/persona/技能/用户指南/README 五类资产联动（定义规则、MOC 标题、1~3 张卡口径、测试计数）。先 grep 关键词（`30 字`、`1~3`、`import fitz`、`96 项`、`知识目录_日期`）确定全部落点，一次改完，最后残留 grep 兜底（沿用 2026-08 T6）。

### T8. 环境故障"三步处置"（本次验证有效）
kill 挂起进程 → 只读诊断（`pnpm store path`、`.pnpm` 目录完整性、`.modules.yaml` 状态）→ 定位根因类别（沙箱/网络/锁）；**根因未明不重试**。本次根因明后，同一条命令 755ms 通关。

## 三、一句话总结

本次可避免浪费的 **~70% 集中在"版本号先行"触发的 pnpm 重装事故**（叠加沙箱限制放大了 3 倍），其余为两处小笔误（TS 键引号、Copy-Item 嵌套）——**逻辑返工为 0 轮**。最值钱的三条纪律：**版本号是最后一刀、受限命令先探路、工作区外数据先备份+唯一锚点校验**。若把这三条前置，本次本可省掉约四十分钟与三分之一的往返。

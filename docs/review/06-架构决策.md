# 六、架构决策合理性校验（挑战式评审）

> 立场：不预设"重构 = 进步"。以下逐条质疑本次重构（`1c71773` → `8e03995`）的动机、达成度、代价与替代方案。

---

## 6.1 当前重构解决的真实核心业务问题是什么？是否最简？

**真实问题（从 persona / 用户指南 / 提案反推）**：
1. **知识库腐化**——卡片写进 vault 之后没有任何质量约束，模型每次会话可能写出"你/我们/上次讲到/本工程实测/L182 行"这类**会话残留**，半年后卡片不可读；
2. **格式漂移**——同一套模板套所有卡（一边臃肿一边空洞）、版本更新被追加到文件末尾（阅读顺序错乱）、关联行格式五花八门；
3. **维护成本**——改标题要手工同步文件名与全库入链，历史块只能手工删。

**方案的形状**：`cardmodel`（段落模型）→ `template`（声明式模板）→ `lint`/`lintrules`（规则引擎）→ `history`/`rename`（维护工具）→ `tools`（薄适配）→ `index`（编排）。

**评审结论：方向是最简的，实现不是。**
- 方向层面**值得肯定**：没有引入数据库、索引服务、事件总线、后台任务；数据仍是"带 frontmatter 的 .md"，符合 Obsidian 用户的心智模型；5 个新模块都是纯函数（除 `history`/`rename` 的 IO 在 `index` 侧），依赖无环。这是**正确的最小架构选择**。
- 但实现层面有 3 处"超出问题需要的复杂度"：
  1. **14 条规则里有 5 条本质是"小节是否存在"**（`template-sections`/`mainline`/`walkthrough`/`reentry-point`/`prereq-check`），完全可由 `template.ts` 的 `required/optional/mainline` 规格推导（EXT-2）。现在等于把同一份规格手抄了两遍。
  2. **100 分制打分是伪精确**：权重 3~10、error 封顶 59（`src/lint.ts:77-92,279`）——没有任何外部真值校准"62 分"和"75 分"的区别。它带来的真实行为是**用户/模型为凑分返工**，而不是"卡片更好读"。更简的替代是"通过/缺失"清单 + 少量高置信度正则。
  3. **`mainline` 字段定义了却没人读**（`src/template.ts:21`），说明"规格驱动"的意图只落地了一半。

**挑战点**：如果目标是"半年后还能读懂"，最有效的杠杆其实是**会话残留检测 + 模板必填小节**这两条（对应 P0 的 ①③），其余 9 条规则是长尾。把长尾也做进同一套打分体系，收益递减而维护成本线性上升。

## 6.2 本次重构主要在优化什么？是否达成？

| 目标维度 | 重构做法 | 达成度 | 证据 |
| --- | --- | --- | --- |
| 业务迭代效率 | 模板/规则集中到 `template.ts`/`lintrules.ts` | **部分达成** | 模板是数据驱动（好）；但规则新增仍要改 4~5 处（EXT-1），`mainline` 未生效（EXT-2） |
| 数据一致性 | 版本块插到「关联卡片」前；关联行归一；改名同步入链 | **部分达成，且新引入破坏** | 版本块位置正确（`tests/history.spec.ts:26-48`）；但 `stripHistory` 会删错内容（BIZ-1）、`rename` 半写盘（BIZ-2） |
| 可检测性 | 新增 `card_lint` + cross/trend/rating | **达成** | 14 条规则 + 3 个分析视图，单卡/批量均有报告 |
| 延迟/性能 | 未涉及 | **未优化，略有退化** | 每次调用仍全库扫描（PERF-1）；新增 3 个工具把触发次数从 9 提到 12；lint 重复读盘（PERF-2） |
| 可扩展性 | 分层：model/template/lint/tools/store | **方向达成，扩展点未收敛** | `VaultStore` 517 行上帝类（EXT-4）；领域族硬编码（EXT-3） |
| 可维护性 | 抽出 5 个模块、注释详尽 | **达成（有例外）** | 模块边界清晰、注释密度高；但 persona 重复段落（CPLX-9）、死导出（CPLX-8）、工具描述与实现不符（CPLX-9） |

**结论**：本轮是**"业务可检测性"驱动的重构**，而不是"性能/架构"重构。以此为目标，达成度约 60%：可检测做到了，可维护只到"能改"，一致性目标反而被 BIZ-1/BIZ-2 拖成负分。

## 6.3 重构之后引入了哪些全新的故障与复杂度隐患？

1. **行号坐标系混用 → 数据丢失**（BIZ-1）。这是全新引入的：重构前 `card_history` 不存在，也就不存在"用旧行号删新文本"这条路径。
2. **多文件写盘无事务**（BIZ-2）。`rename` 是全库写操作，失败点在中途，且没有回滚。
3. **同一份文档存在三种改写路径**：`insertBlockBefore`（`cardmodel.ts:119`，字符串拼接）、`addLink`（`card.ts:295`，字符串拼接）、`stripHistory`（`history.ts:157`，行号删除）、`replaceCardTitle`（`rename.ts:19`，正则替换 frontmatter）。**没有统一走段落模型**——`cardmodel` 的定位是"地基层"，但真正需要它的 `addLink`/`stripHistory` 反而是手写字符串/行号逻辑。这是架构意图与实现的最大偏差。
4. **正则 lint 的误报成本被放大到"分数"**：`实测`/`我们` 每处扣 10 分（`src/lintrules.ts:18,20`），`residueLevel=error` 时封顶 59（`src/lint.ts:279`）。一张 100 分的好卡因为一句"实测帧率"变成 90，因为"我们如何验证"再降到 80；模型看到"未通过"会去改卡片——**用不可靠的信号驱动返工**。
5. **固定 prompt 开销上升**：工具从 9 → 12，`card_lint` 的描述 400+ 字（`src/tools.ts:264-281`），`card_create` 的 `content` 描述新增模板要求（`src/tools.ts:129-134`）。本项目历史上专门做过"T3 精简"（见 `README.md:29` 与 `docs/archive`），本轮方向与之相反——需要权衡：新增能力 vs 每轮固定 token。
6. **测试与实现同源，回归保护弱**：`tests/skills.spec.ts` 只断言 SKILL.md 里"出现某些关键词"，不断言与代码/配置一致；`tests/history.spec.ts:90-123` 的用例恰好掩盖了 BIZ-1。209 个测试全绿，但**最关键的数据删除路径与文档一致性都没有被真正约束**。
7. **新模块的"纯函数"承诺被打破**：`splitSections` 依赖模块级带 `g` 的正则状态（CPLX-10）；`SearchIndex.all()` 泄露内部数组（CPLX-6）。这类问题在单测下不显形，在多工具并发（`isConcurrencySafe: () => true`，`src/tools.ts:73,92,107,284`）时才会暴露。

## 6.4 如果发现重构不合适，回退/改造的成本有多高？

**代码层：低（< 1 人日）**
- 新增文件：`src/cardmodel.ts`、`src/template.ts`、`src/lint.ts`、`src/lintrules.ts`、`src/history.ts`、`src/rename.ts`、`src/tools.ts`（`tools.ts` 是从 `index.ts` 抽出的，不算纯新增）。
- `index.ts`/`card.ts`/`frontmatter.ts`/`vault.ts` 的改动是**接线与扩展**，没有推翻原有数据流（`refresh`/`resolveCard`/`atomicWrite` 完全没动）。
- 回退方式：`git revert 8e03995` 或 `git checkout 1c71773 -- src presets`，工具集回到 9 个，`lib/` 重新构建即可。

**数据层：单向，但向后兼容**
- 已落盘的新格式：frontmatter 新增 `模板:` 字段、`- 前置：\`标题\`（ID）` 归一格式、`### 版本更新` 插入位置、`<details>` 历史折叠块。
- 旧代码不认这些：`parseFrontmatter` 忽略未知键（`src/frontmatter.ts:33-45`），`<details>` 只是普通正文，**不会损坏**。
- 真正不可逆的只有一项：**若已经用 `card_history strip` 删过内容**（BIZ-1），丢失的正文无法恢复（除非 vault 在 git/版本控制里——README 建议用户用 git 管理 vault，这算是最后的保险）。

**结论**：这次重构属于"低回退成本、高收益"的类型，架构选型**不是**需要推翻重来的问题；需要修的是实现缺陷（BIZ-1/2）与扩展点收敛（EXT-1/2/4），而不是回退。

## 6.5 是否存在更小、更简单的替代设计方案？

**A. 结构检查取代打分（省 ~40% lint 代码）**
保留 `cardmodel` + `template`，lint 只输出"通过/缺失"清单 + 3 条高置信度正则（会话残留的路径/行号/时间词）。删除权重、封顶、100 分制、`distribution`/`averageScore`。收益：消灭"凑分返工"，`card_lint` 描述可缩短一半。

**B. `strip` 改为"整卡重写"（直接消灭 BIZ-1）**
读卡 → `splitSections` → 过滤目标小节 → 在 section.body 上删 details 块 → `renderSections` → 写回。不引入任何行号坐标。代码量相当，风险归零。

**C. `rename` 降级为"改标题 + 报告待处理入链"（消灭 BIZ-2 与 PERF-5）**
默认只改本卡 frontmatter/文件名，全库入链重写改为显式 `rewriteLinks: true`；报告里列出"以下 N 个文件仍引用旧标题"。收益：单次操作从"全库写"降为"单文件写"，事务问题自然消失。

**D. 合并维护工具（12 → 10 个工具）**
`card_lint` + `card_history` + `card_rename` → `card_maintain(action: 'lint'|'history'|'rename', ...)`。收益：固定 prompt 开销下降（与 T3 精简方向一致）；代价：单工具 schema 变复杂、模型选择分支的成本转移到参数上。**建议不做**，因为学习会话里三个动作的触发语境差异大，合并反而降低工具选择准确率——这一条是"更小但未必更好"的典型，记录下来供后续权衡。

**E. 不做 `cross`/`trend`/`rating` 三个分析视图**
它们是 P2 增量（`README.md:29`），使用频次低（需要用户主动问"卡片质量/口径是否一致"），但每次都要全库 `extractFacts`。若观察一段时间无人使用，删除可省 223 行 + 全库扫描成本。

## 架构维度小结

| 问题 | 结论 |
| --- | --- |
| 方案是否解决真实问题 | 是。腐化/漂移/维护成本是真问题，段落模型 + 声明式模板是正确的最小选择 |
| 是否最简实现 | 否。规格被抄成两套；打分制是伪精确；`mainline` 字段未生效 |
| 主要优化方向 | 业务可检测性（达成）；性能未优化且有退化；扩展点未收敛 |
| 新引入的隐患 | 行号坐标系混用（数据丢失）、多文件写无事务、四种改写路径并存、误报驱动返工、prompt 固定开销上升、测试与实现同源 |
| 回退成本 | 代码 < 1 人日；数据向后兼容；唯一不可逆是已执行的 `strip` |
| 更小的替代方案 | A（结构检查取代打分）、B（strip 整卡重写）、C（rename 降级）均值得采纳；D（合并工具）建议不做 |

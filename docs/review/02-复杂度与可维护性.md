# 二、复杂度与可维护性

> 度量口径：函数长度按源码行计（含签名与闭合括号）；圈复杂度按分支点（`if`/`? :`/`??`/`||`/`&&`/`catch`/循环）粗估；嵌套层级按语句块缩进计。
> 总体判断：**模块切分方向是对的**（纯函数 + 一个状态类，无循环依赖，typecheck 干净），但**热点函数已经明显过载**，且"文档与实现两套口径"的问题已经出现（见 CPLX-9）。

---

## CPLX-1 `VaultStore.rename()` 80 行、嵌套 4 层、圈复杂度 ≈20

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:471-550`。单函数同时承担：解析引用 → 同名冲突检查 → 生成改名计划 → 改本卡标题 → 全库遍历 → 逐文件解析/重写入链 → 只读根判定 → dryRun 分支 → 写盘 → 改文件名 → 生成报告。
  - 嵌套最深点在 `src/index.ts:496-531`：`for` → `try/catch` → `if (isCard)` → `if (changedCount === 0)`/`if (file.root !== 'vault')` → `if (opts.dryRun)`（4~5 层）。
- **WHY**：认知负担高、改动风险大（任何一处顺序调整都可能触发 BIZ-2 的半写盘）；`dryRun` 与实写两条路径**各自维护一份 changed/broken 收集逻辑**（`525-531`），已经产生行为不一致（dryRun 的断链检测恒为空，见 BIZ-10）。
- **FIX**：拆成三个纯/半纯步骤，保持行为不变：
  1. `planRenameTargets(card, title, plan, index)` → 返回 `{writes, broken, changed}`（不落盘）；
  2. `commitRename(card, selfText, writes, plan)` → 统一落盘（含目标名冲突的**前置**校验）；
  3. `rename()` 只做编排 + 报告。
  嵌套可用"早 continue"压平：`if (changedCount === 0) continue` 提到循环体开头。

## CPLX-2 `VaultStore.lint()` 79 行、8 个早返回分支

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:367-445`。单函数覆盖 5 种输出形态：单卡、单卡+规则、批量、批量+规则、cross、trend、rating（`392-444` 连续 6 个 `if ... return`）。
- **WHY**：新增分析视图（例如"按领域统计"）只能继续往这里塞分支，函数会持续膨胀；且 `reportOf` 闭包捕获 `ctx`，与下面的批量读盘逻辑耦合在同一个作用域，测试粒度只能是端到端。
- **FIX**：抽 `lintOne(ref)` / `lintBatch(scope)` / `lintByRule(rule)` / `lintCross()` / `lintTrend()` / `lintRating()` 六个返回字符串的函数，`lint()` 只做路由（`if (opts.ref) return ...`）。零行为变化。

## CPLX-3 `lintCard()` 158 行、14 个顺序 `if` 块、圈复杂度 ≈30

- **SEVERITY**：warning
- **WHAT**：`src/lint.ts:132-289`。规则判定、权重扣分、封顶、字数统计、`passed` 记录全部内联在一个函数里；每条规则的结构是 `if (!off.has(id)) { 计算; findings.push(...); mark(id, ok) }`，重复 12 次。
- **WHY**：这是全仓最长的函数，也是**最常被改**的地方（14 条规则）。新增/删除规则要动 4 处（`WEIGHTS`、`RULE_TITLES`、此处 `if` 块、`src/tools.ts:277` 的枚举）；同时它与 `EXT-1`/`EXT-2` 是同一个根因。
- **FIX**：表驱动化，保持所有现有判定函数不动：
  ```ts
  type Rule = { id: RuleId; run: (ctx: RuleCtx) => { ok: boolean; findings: LintFinding[] } }
  const RULES: Rule[] = [ { id: 'session-residue', run: ... }, ... ]
  // lintCard: for (const r of RULES) { if (off.has(r.id)) continue; const out = r.run(ctx); ... }
  ```
  `ctx` 预计算 `sections`、`blankOutBlocks` 结果、`bodyLength`（顺带修掉 PERF-3）。

## CPLX-4 `scanResidue()` 每行 6 个正则 + 4 层白名单判定

- **SEVERITY**：warning
- **WHAT**：`src/lintrules.ts:61-97`。`lines.forEach` 内：行号正则 + 3 个邻近性判断（`73-79`）→ 路径正则 → 非引用块时再跑 5 个正则 + 里程碑特判（`83-94`）。圈复杂度 ≈14（回调内），嵌套 3~4 层。
- **WHY**：这是 `card_lint` 的 P0 规则，误报直接影响用户体验（每条扣 10 分）。规则与白名单以"内联 if 链"存在，新增一条残留类型（例如"章节编号漂移"）要在这段里再插一个正则 + 一个白名单分支，回归风险高。
- **FIX**：改成数据表 + 单次遍历：
  ```ts
  const RULES = [
    { rule: 'path', re: RESIDUE_PATH_RE, guard: null, scope: 'all' },
    { rule: 'line', re: RESIDUE_LINE_RE, guard: lineNumberGuard, scope: 'all' },
    { rule: 'person', re: RESIDUE_PERSON_RE, scope: 'nonQuote' }, ...
  ]
  ```
  每行 `for (const r of RULES)` 一次判断，白名单作为 `guard(line, m)` 回调。

## CPLX-5 `VaultStore.memory()` 64 行、嵌套 4 层

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:591-654`。`get` 分支里再嵌 `if (fields.key !== undefined)`（600-613）；`_autoPrefs` 特判里再嵌 `append`/`remove`/`set` 三层（618-635）；嵌套最深 `618 → 620 → 621`（4 层）。
- **WHY**：控制键（`_autoPrefs`）与普通键两条路径逻辑高度相似却各写一遍（`remove` 分支重复 `hasOwnProperty` 判断两次），后续新增第二个控制键时几乎必然复制粘贴。
- **FIX**：抽 `readNote` / `writeNote` / `removeNote` / `setControlKey` 四个小函数；`memory()` 只做 action 路由。

## CPLX-6 隐藏副作用：名为"查询/刷新"，实为全库 IO 与状态重建

- **SEVERITY**：warning
- **WHAT**：
  - `src/index.ts:184-205` `refresh()`——名为刷新缓存，实为 `walkRoots` 全库遍历 + 全文件 `stat` + 全文件 `readFile` + 索引重建（每次工具调用都会触发）；
  - `src/index.ts:231-234` `get()`、`218-224` `search()`、`367` `lint()`、`448` `history()`、`471` `rename()` 都会间接触发它；
  - `src/search.ts:180-182` `all()` **直接返回内部 `cards` 数组引用**，调用方（`src/index.ts:227`、`405`）虽只读，但接口本身允许外部变异索引。
- **WHY**：违反"命名即契约"。调用方以为 `card_get` 只读一个文件，实际每次都 stat 全库（PERF-1 的根因）；`all()` 返回内部引用是典型的**未来事故点**（某天有人 `index.all().sort()` 就地排序，索引顺序即被打乱，而 `inverted` 里存的是下标）。
- **FIX**：
  - `refresh` → `ensureIndex()`，并在 JSDoc 明确"每次调用都会 stat 全库"；再加 TTL 缓存（PERF-1）；
  - `all()` 返回 `readonly IndexedCard[]`（TS 层面）或 `return [...this.cards]`。

## CPLX-8 死代码 / 仅测试使用的导出 / 重复实现

- **SEVERITY**：nit
- **WHAT**（`grep` 全仓结果，排除定义处）：

| 符号 | 位置 | 状态 |
| --- | --- | --- |
| `TEMPLATE_SECTIONS` | `src/card.ts:14-18` | **0 引用**（注释说"避免破坏既有调用方"，但仓内无调用方） |
| `sectionBody` | `src/cardmodel.ts:97-100` | **0 引用** |
| `hasHeading` / `headingLine` | `src/cardmodel.ts:102-113` | 仅 `tests/cardmodel.spec.ts` 使用 |

| `byRel` | `src/search.ts:209-211` | 仅 `tests/search.spec.ts` 使用 |
| `sanitize()` | `src/rename.ts:126-134` | `sanitizeFilename()` 的**第二份实现**（漂移风险，见 SEC-3） |
| `parseFrontmatter(rewritten)` | `src/index.ts:485-486` | 同一文本解析两次 |

## CPLX-9 文档与实现口径漂移（重构后已出现 3 处）

- **SEVERITY**：warning
- **WHAT**：
  1. `src/tools.ts:275` 工具描述："`all`=含旧笔记（**旧笔记无模板要求**）"，实现 `src/index.ts:405-423` 对旧笔记照样套理论型模板 → 实测（探针 P5）旧笔记得 62/100，命中「模板必填小节 ×6」「主干线唯一」「实例走查」；
  2. `presets/study/agent.cordis.yml:58-70`：`## 格式红线` 整段**重复两遍**（58-61 与 67-70 内容逐字相同），每轮请求都多付一份固定 token，且将来只改一处就会产生互相矛盾的 persona；
  3. `src/template.ts:161`/`166` 注释称 `sectionHints`/`templateTable` "工具描述共用"，实际 `tools.ts` 手写描述（见 CPLX-8）。
- **WHY**：persona 是模型行为的唯一权威来源，重复段落会让"改一处生效一半"；工具描述与实现不符会让模型做出错误决策（这里会让模型以为 `scope=all` 是安全的批量视图，实际得到一堆噪声报告，进而浪费一轮返工）。
- **FIX**：① 删掉 persona 的重复段落（`58-61` 保留一份）；② 实现与描述二选一对齐——推荐实现向描述对齐：`reportOf` 对 `kind === 'note'` 跳过结构类规则（`template-sections`/`mainline`/`walkthrough`/`reentry-point`/`prereq-check`/`verify-experiment`/`troubleshoot-criteria`/`layer-number`/`selftest-answer`），只保留通用规则；③ 让 `tools.ts` 用 `templateTable()` 生成描述。

## CPLX-10 模块级带 `g` 的正则 + 手动 `lastIndex`

- **SEVERITY**：nit
- **WHAT**：`src/cardmodel.ts:31` `const HEADING_RE = /^(#{1,6})[ \t]+(\S.*?)[ \t]*$/gm`，`src/cardmodel.ts:40` 在函数内 `HEADING_RE.lastIndex = 0` 后循环 `exec`。
- **WHY**：当前是同步、单线程、无提前 `return` 的循环，**暂时安全**；但这是典型的"共享可变正则状态"反模式——一旦将来在循环里加 `break`/抛错，或有人把 `splitSections` 改成 async/可重入，就会静默错位（漏小节）。
- **FIX**：改用 `for (const m of text.matchAll(HEADING_RE))`（`matchAll` 内部克隆正则，无共享状态），删掉手动 `lastIndex`。

## CPLX-11 测试盲区：`stripHistory` 的"全清"用例恰好掩盖了行号漂移缺陷

- **SEVERITY**：warning
- **WHAT**：`tests/history.spec.ts:90-123` 断言"清除全部历史块并保留主线与关联"，但该用例把 `<details>` 放在**勘误小节内部**——`splitSections` 会把它并入勘误小节，删除勘误小节时 details 已一并消失，于是 `dropDetailsBlocks` 的旧行号永远命中不到目标（`targets.has(lineNo)` 恒 false），测试通过。
  - 实测（探针 P2/F）：把 `<details>` 放在「易错点」之后或手改卡多一个空行时，同一函数会删掉 `旧正文`、`</details>` 乃至整个 `### 关联卡片`（详见 BIZ-1）。
- **WHY**：这是"绿灯掩盖数据丢失"的典型。当前 209 条测试全绿，但**最关键的数据删除路径实际未被覆盖**。
- **FIX**：补两条回归用例（会立刻变红，配合 BIZ-1 修复）：
  1. version 小节在 details 之前、且 details 不属于任何被删小节；
  2. 小节之间存在连续空行（手改卡常见形态）时的 `strip({kinds:['details']})`。
  断言"删除后 `### 关联卡片` 与关联行仍在、且不存在未闭合 `<details>`"。

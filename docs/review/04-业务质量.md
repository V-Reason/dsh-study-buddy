## BIZ-1 `card_history strip` 用「旧行号」删除「重排后文本」，会删掉无关正文（数据丢失）

- **SEVERITY**：**blocker**
- **WHAT**：
  - `src/history.ts:157-176` `stripHistory()`：先 `extractHistory(text)` 得到**原始正文**里 `<details>` 块的行号（`src/history.ts:63-106`），再 `renderSections(lead, kept)` **重排文本**（去掉空行、去掉 version/errata 小节），最后把旧行号交给 `dropDetailsBlocks(next, ...)`（`src/history.ts:133-150`）按行删除。
  - 两套坐标系不一致：`renderSections`（`src/cardmodel.ts:60-71`）会折叠多余空行、统一小节间空行，删除 version/errata 小节后**其后所有行号前移**。
- **WHY**（两条实测证据，均可复现）：
  - **探针 P2**：正文含 `### 版本更新` 且 `<details>` 位于其后的「易错点」小节内 → `removed = [{version, 6-9}, {details, 12-17}]`；删 version 后文本只有 11 行，`dropDetailsBlocks` 拿 12-17 去删 → 循环直接跳到末尾，结果**丢掉了 `旧正文`、`</details>`、以及整个 `### 关联卡片` 小节**，且留下未闭合的 `<details>`。
  - **探针 F**：卡片小节之间多一个空行（Obsidian 手改卡的常见形态）→ 同样删错，结果以裸 `<details>` 结尾，`<summary>` 与正文全部丢失。
  - 触发条件很宽：只要 `<details>` 不在被删的 version/errata 小节内部（**`card_update replace` 产生的历史折叠块正是追加在文末，属于这种情况**），或文本空行不规范，就会命中。
  - 现有测试 `tests/history.spec.ts:90-123` 因为把 details 放在勘误小节内而恰好不触发（见 CPLX-11），所以 CI 全绿。
- **FIX**（最小改动，保持现有 API）：改为"两遍段落模型删除"，彻底不依赖行号：
  1. 先删 details：在 `splitSections(text)` 的每个 section.body 里按 `<details>`/`</details>` 配对定位并移除（或对原始 `text` 调 `dropDetailsBlocks`，此时行号与 `extractHistory` 同坐标系）；
  2. 再 `splitSections` 一次，过滤掉 `^版本更新`/`^勘误` 小节；
  3. `renderSections(lead, kept)`。
  顺序反转即可让两次删除各自使用**同一坐标系**；`dropDetailsBlocks` 的调用点从"重排后"移到"重排前"。

## BIZ-2 `card_rename` 多文件写盘无事务：目标名冲突时已发生半写盘

- **SEVERITY**：**blocker**（数据一致性）
- **WHAT**：`src/index.ts:536-547` 的提交顺序是：① `atomicWrite(card.path, selfText)`（本卡新标题）→ ② `for (const write of writes) atomicWrite(...)`（全库入链重写）→ ③ 若 `plan.renameFile` 才检查目标文件名是否已存在，存在则 `throw`。
  - 即**冲突校验发生在所有写入之后**。
- **WHY**（探针 P7）：手工放一个同名文件 `CCC.md`（标题不同，因此 `index.byTitle` 的同名检查抓不到）后调用 `rename(idA, 'CCC')`：
  - 抛出 `目标文件名已存在：CCC.md`；
  - 但此时 `AAA.md` 的 frontmatter 标题**已被改成 `CCC`**；
  - 引用它的 `BBB.md` 里的关联行**已被重写**为 `` `CCC`（id） ``，指向一个不存在的文件名；
  - 文件本身仍叫 `AAA.md`。
  - 结果：用户看到"失败"，实际库里已是**标题/文件名/入链三者互相矛盾**的状态；若同时命中了 MOC 的 wikilink 重写（`src/index.ts:511-516`），`[[AAA]]` 也会变成打不开的 `[[CCC]]`。这类不一致不会自愈，且 `card_lint`/`card_search` 都不会报警。
- **FIX**：把"决策"与"提交"彻底分离（配合 CPLX-1 的拆分）：
  1. 先算出全部目标路径（本卡新路径 + 每个待写入文件路径）并做**全部冲突校验**（`fileExists(targetPath)`、`index.byTitle`）；
  2. 再依次写入；
  3. 失败时按已写文件列表回滚（`atomicWrite` 前先读原文缓存，出错时写回）。
  最小可用版本：把 `542` 的 `fileExists` 检查提前到 `536` 之前，即可消除"标题已改但文件没改名"这一半写盘。

## BIZ-3 `card_update` 不接受会话 cwd，`card_search` 回显的路径无法直接用于更新

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:283-292` `update(id, payload)` 无 `call?: {sessionCwd}` 形参，`src/tools.ts:216` 也只用 `args.id`。而 `card_get`/`card_link`/`card_moc`/`card_lint`/`card_history`/`card_rename` 都传了 `sessionCwdOf(exec)`。
- **WHY**（探针 C2）：开启 `includeSessionCwd` 后，`card_search` 命中工作目录里的旧笔记并回显 `- 路径：工作目录/note.md`；用户/模型紧接着调 `card_update` 用同一路径 → **`找不到卡片 "工作目录/note.md"`**，而同样路径传给 `card_get`/`card_history`/`card_link` 都正常。对模型来说这是"工具时好时坏"，会诱发反复试探、浪费轮次，最后往往放弃更新。
- **FIX**：`update(id, payload, call?: { sessionCwd?: string })`，`resolveCard(id, call?.sessionCwd)`；`src/tools.ts:216` 改为 `store.update(String(args.id ?? ''), payload, { sessionCwd: sessionCwdOf(exec) })`。顺带把 `create`/`progress`/`memory` 是否也需要 cwd 明确一次（目前不需要）。

## BIZ-4 `card_lint scope=all` 与工具描述相反：旧笔记被套模板规则

- **SEVERITY**：warning
- **WHAT**：`src/tools.ts:275` 描述 `all=含旧笔记（旧笔记无模板要求）`；实现 `src/index.ts:405-423` 对所有条目统一 `reportOf()` → `lintCard({ template: parsed.meta?.template })`，旧笔记无 `模板:` → `templateSpec(undefined)` 回退理论型（`src/template.ts:91-94`）。
- **WHY**（探针 P5）：一篇 11 字的旧笔记得 **62/100**，命中「模板必填小节 ×6」「主干线唯一」「实例走查」。批量报告会把旧笔记全排进"最低分"列表，均分被拉低，用户按报告去"整改"旧笔记毫无意义；更糟的是模型可能真的去给旧笔记补模板小节（把随手笔记改造成卡片），属于**业务语义错位**。
- **FIX**：`reportOf` 接收 `kind`，`kind === 'note'` 时只跑通用规则（`session-residue`/`definition-length`/`code-language`/`links-format`/`domain-tag`），并在批量报告里把旧笔记单列一行"（旧笔记仅体检通用规则）"。

## BIZ-5 `card_lint rule=...` 在规则被禁用时输出"✗/⚠ 未通过（该规则无发现）"

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:395-400`：`const passed = report.passed[opts.rule]` → 规则被 `lint.rulesOff` 关闭时 `passed` 为 `undefined` → 三元表达式走 `'✗/⚠ 未通过'`，同时 `hits.length === 0` 输出"（该规则无发现）"。
- **WHY**（探针 P6，配置 `rulesOff: ['walkthrough']`）：
  ```
  卡片：X  规则：walkthrough  ✗/⚠ 未通过
    （该规则无发现）
  ```
  自相矛盾的输出。用户会认为卡片有问题去改，或认为工具坏了；模型可能据此改写卡片——**在配置层面关闭的规则反而导致了返工**。
- **FIX**：`if (passed === undefined) return \`卡片：${report.title}  规则：${opts.rule}  （该规则未启用或无判定，检查 lint.rulesOff）\``。

## BIZ-6 `card_link` 去重范围是整篇正文，静默跳过真实关联却报告成功

- **SEVERITY**：warning
- **WHAT**：`src/card.ts:300-306`：`existing` = **正文所有以 `-` 开头的行**（不限「关联卡片」小节）；判重时把行首的 `前置/后续/易混淆：` 前缀剥掉后与目标标题比较。
- **WHY**（探针 D）：卡片「乙」的「前置检查」小节写了 `- 前置：甲`，随后 `card_link(乙, 甲, prev)`：
  - 「乙」侧被判定为"已存在"，**不写入**；
  - 返回文本却是 `已建立关联：乙（id） ←前置知识→ 甲（id）（已写入 1 侧）`——读起来像成功（只有"1 侧"是唯一线索）；
  - 结果「乙」的「关联卡片」小节缺失，MOC 与后续 `card_lint links-format` 都发现不了（该小节根本不存在）。
  另外 `addLink` 的判重对"ID 命中"也是全正文范围：任何一行末尾括号内容碰巧等于目标 ID 都会被当成已关联。
- **FIX**：用段落模型限定范围：`const links = findSection(splitSections(body).body?...)`，只对 `### 关联卡片` 小节内的行判重；小节不存在时视为"无重复"。返回文本改为区分"新增 N 行 / 已存在 M 行"，避免"已建立关联"这种模糊措辞。

## BIZ-7 静默错误：读盘/遍历失败被吞，报告数字仍然"完整"

- **SEVERITY**：warning
- **WHAT**：
  - `src/index.ts:194-200` 索引重建时 `readFile` 失败 → `catch {}` 跳过；
  - `src/vault.ts:104-107` `readdir` 失败 → 静默 `return`（权限不足的目录整棵子树消失）；
  - `src/index.ts:413-417` 批量 lint 读失败 → `continue`；
  - `src/index.ts:499-503` rename 读失败 → `continue`；
  - `src/vault.ts:116-119` `stat` 失败 → 跳过。
- **WHY**：所有"跳过"都没有计数、没有回显。用户看到 `共检索 223 篇`、`入链：4 个文件`、`批量 lint：223 张卡` 时，无法知道其中有 N 篇因为被 OneDrive 锁定/权限不足/文件正在被 Obsidian 重写而**没有被索引/没有被重写**。对于"改名同步全库入链"这种操作，静默漏改 = 断链，而报告说"断链检测：无"。
- **FIX**：在 `refresh`/`lint`/`rename` 里累计 `skipped: string[]`，并在返回文本末尾追加 `⚠ 跳过 3 个文件（读取失败）：a.md、b.md…`。这是最小成本、最大收益的可靠性改进。

## BIZ-8 `card_create` 不检查同名标题，同一概念可无限重复建卡

- **SEVERITY**：warning
- **WHAT**：`src/index.ts:236-281` `create()` 只通过 `uniqueCardPath` 保证**文件名**唯一（`src/vault.ts:232-241`，冲突时加 ID 后缀），从不检查是否已存在同标题卡片；而 `rename` 会检查（`src/index.ts:481-482`）。
- **WHY**：模型在一次归档里重复建同一张卡（很常见：分两次归档同一小节）→ 库里出现 `漫反射.md` 与 `漫反射_ab12.md` 两张内容重叠的卡，`index.byTitle` 只返回第一张（`src/search.ts:188-191`），`card_link`/`card_update` 会固定改到其中一张，另一张成为"孤儿卡"。MOC 会把两张都收录，用户以为是一张。
- **FIX**：`create()` 前查 `index.byTitle(input.title)`；命中时**不阻断**（避免破坏"故意建多张同名卡"的边缘用法），但在返回文本顶部加显著警告：`⚠ 已存在同名卡片（路径，ID）：建议 card_update 增量更新而非新建`。

## BIZ-9 `opener.hasPriorUserMessage` 注释声称"抛错保守返回 false"，实现无 try/catch

- **SEVERITY**：warning
- **WHAT**：`src/opener.ts:80-95`（注释 `72-79` 明确写"两者皆缺/抛错 → 保守返回 false"）与 `src/index.ts:706-722`（pre-step 钩子在 `await next()` 之后调用它）。
- **WHY**：`session.snapshotEvents()` 是宿主 API，跨版本可能抛错（本项目历史上正因 session API 变更踩过坑，见 `docs/archive/dev-experience/dev-experience-2026-09-platform-adaptation.md`）。抛错会从 pre-step 处理器逸出——按 Cordis 语义这属于**步骤级失败**，最坏情况是首步直接失败（fail-closed），而不是注释承诺的"只多注入一次提醒"。这是"注释即契约"被违反的典型，且没有任何测试覆盖。
- **FIX**：
  ```ts
  try { ... } catch { return false }
  ```
  并补一条测试：`snapshotEvents` 抛错时 `hasPriorUserMessage` 返回 `false` 而不抛。

## BIZ-10 `card_rename` 的 dryRun 恒报"断链检测：无"；实写时断链检测对象错位

- **SEVERITY**：warning
- **WHAT**：
  - `src/index.ts:525-528`：`dryRun` 分支 `continue` 发生在 `broken.push(...)`（`531`）**之前** → dryRun 的 `broken` 永远为空，`formatRenameReport` 输出"断链检测：无"（`src/rename.ts:186-191`）；
  - `src/index.ts:531`：`detectBrokenLinks(nextBody, ...)` 传入的是**其它文件**改写后的正文（本卡被 `497` 跳过），所以实写时的"断链检测"报告的是**别人的**格式漂移行，与本次改名无关。
- **WHY**：dryRun 是用户"预演再决定"的唯一安全网（persona 也强调"先给用户新旧对比"），却给出"无断链"的假保证；实写时报告里冒出一堆无关文件的"关联行格式不符"，会让人误以为改名破坏了这些文件。
- **FIX**：dryRun 分支也执行 `detectBrokenLinks`（放在 `continue` 之前）；把断链检测对象改为**本卡改写后的正文**（在 `selfText` 上检测），或明确改名报告字段为"扫描范围内其它文件的关联行格式问题"。

## BIZ-12 业务逻辑与 persona 的其它不一致（抽样）

- **SEVERITY**：nit
- **WHAT**：
  - persona（`presets/study/agent.cordis.yml:61`）说"定义 31~60 字允许放行不返工"，`card_lint` 的 `definition-length` 只在 `>60` 时报警（`src/lint.ts:157-163`），但 **31~60 字不报警**——两者一致，属于正确对齐；
  - 而 persona `:59` 要求"单块 ≤60 行""列数 ≤4"等格式红线，`card_lint` 14 条规则里**没有任何一条检查这些**（代码块长度、表格列数）——模型被要求做的事没有任何自动校验；
  - persona `:56` 要求"小节之间用因果连接，禁止『下面我们看…』"，`RESIDUE_SESSION_RE` 未覆盖该句式。
- **WHY**：persona 的格式红线是"人工约定"，lint 覆盖不到的部分只能靠模型自觉；一旦模型漂移，用户没有任何工具能发现（`card_lint` 给 100 分，但卡片实际违反 persona 要求）。这不是缺陷，而是**能力边界未对用户说明**。
- **FIX**：在 `card-format` 技能与 README 里明确"`card_lint` 覆盖的 14 条 vs persona 人工约束"的边界；若希望覆盖，加两条低成本规则：代码块行数 >60、表格列数 >4。

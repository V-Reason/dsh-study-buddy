## 2. 执行不顺利 / 返工记录

### 2.1 定义 ≤30 字软提示 → 全量 read+edit 返工（复现并升级，P1，**建议本次落地**）

- 现象：7 张卡定义全部触发"建议精简"但**不阻塞**；前次报告（B17）我"选择继续落盘"，本次我为全面达标**逐张 read+edit 修正**（7 张 × 2 次文件操作 = 14 步），加上 2.2 的拒绝轮次，归档环节纯返工约 3 轮。
- 判断：软提示 + 两种执行风格（放过/改造）都产生成本；**"定义 ≤30 字"对概念类卡片确实偏紧**（本次 4 个领域键定义 31~62 字区间）。
- 建议（二选一，务必落地）：①>30 字硬拒绝并回显改写建议；②放宽至 50~60 字并把提示等级化。消除"执行风格分叉"。

### 2.2 card_create 产物对 edit 的"须先 read"判定（新增，P1）

- 现象：同一批 5 个 edit（刚用 card_create 落盘的卡，全文与路径已在工具返回值中），4 个被拒"requires reading first"；只能再 read 4 个文件（各 12 行）后重试。
- 根因：edit 的"本会话已创建/已编辑"豁免只认 write/edit 工具自身，**不认 card_create/card_update/card_moc 的产物**；而"建卡→微调定义"是高频组合（本次 7 次）。
- 建议：card_create/card_update/card_moc 成功返回后，把产物文件登记进"本会话已读"集合（或 edit 判定时把工具产物视为"已知内容"）。

### 2.3 PDF 长段提取仍截断（复现上次 2.3，P2，建议硬约束）

- 现象：一次提取 23 页（18 章全部）输出仍被截断，靠补读 2 段找回。上次报告的教训（>10 页分次）**执行层未能吸收**——因为 18 章本身 23 页，我一次传了范围。
- 判断：靠 agent 自觉不可靠；技能模板的"默认 10 页"只是参数说明。
- 建议：file-reading 技能把">10 页必须分次调用"写成固定约束句式（PPT/PDF 模板里明确"单次调用页数上限 10；超限拆分"）；另在截断提示里加一句"优先 read 转储文件补读，而非重跑命令"（本次重跑等价但多花一轮）。

### 2.4 MOC 日期与 card_id 日期相差一天（新增疑点，P1）

- 现象：同在 09-02 的会话中，card_create 生成 ID `202609020541_*`，而 card_moc 落盘文件名与正文日期均为 `2026-09-01`。归档文件按日期排序会错位一天。
- 根因（需排查）：两工具日期源不一致（MOC 可能取会话开始时间/静态默认值/不同时区）。
- 建议：统一日期源；MOC 落盘前回显"文件名+标题+日期"供复核（与 B17 报告 card_moc 预览建议合并实现）。

### 2.5 memory-auto 透明标注遗漏（新增，P2 合规偏差）

- 现象：自动更新 prefs.学习计划（用户拍板精简 PBR 计划）时，回复末尾**未按规范标注**"（已自动记入偏好：prefs.x）"。
- 建议：memory-auto 技能加清单化检查项：任何 set prefs.* 成功 → 必须输出标注行（本次靠记忆即可知遗漏，但应防呆）。

### 2.6 web_search 首轮质量一般（观察，P2）

- 现象：首轮 4 查询打包，返回源以中文 CSDN/公众号为主、契合度低；第二轮单主题查询明显更准。
- 建议：文档化本场景查询策略——每个主题独立查询；涉及 Unity 官方事实（API/版本行为/弃用公告）优先 `site:docs.unity3d.com` 或官方 doc 域名直查。

### 2.7 小项

- glob 全树 `**/*` 返回 805 条截断（有 spill 提示，工具行为正确）；改为 `*.pdf`/`*.pptx` 一次命中——**无返工，仅记录**：全树 glob 信息量低时优先用带扩展名模式。
- card_moc 标题笔误（上次）与中文引号清洗问题本次未触发。

## 一、两轮审查结论（速览）

**首轮（对象 `8e03995` / v0.8.0，报告 01~06）**：方向正确——段落模型 + 声明式模板 + 规则引擎，没有引入数据库/服务/事件总线，数据仍是普通 `.md`，回退成本 < 1 人日；
但"数据一致性"净收益为负：3 个 blocker（`card_history strip` 删错正文、标题/定义换行注入截断 frontmatter、`card_rename` 半写盘）+ 关键 warning 若干，合计 47 项发现。

**复审（对象 `c5c6bbf` / v0.9.0，报告 07）**：3 个 blocker **全部真修复**且通过探针验收（含 rename 回滚路径实测）；
47 项中 **38 项 ✅ 真修复、5 项 🟡 部分修复、2 项 ⏭️ 明确不做、1 项 📄 文档化、1 项 ⏭️ 无需动作**（理由均成立）。
**但修复本身新引入 3 个副作用**（N1 `card_link` 半写盘、N2 `card_create` 性能回归、N3 索引 TTL 可见性回归）+ 12 条 nit，
**已在 v0.9.1 全部修复**（逐条见 §三）。

### 不应被推翻的部分（复审确认，后续重构勿误伤）

- **`cardmodel` 段落模型**：方向正确，`insertBlockBefore`/`matchesTitle`/`blankOutBlocks` 语义清晰且有单测；首轮的缺陷是**没有被 `addLink`/`stripHistory` 真正复用**，正确做法是扩大使用面而不是回退。
- **`template` 声明式规格**：数据驱动的正确做法，只需让 lint 也读它（EXT-2 已完成）。
- **`tools.ts` 从 `index.ts` 抽离**：让"提示词资产"与业务逻辑分文件演进。
- **fail-loud 的挂载策略**：配置错误直接抛错而不是静默不注册工具，是踩过坑之后的正确选择。
- **`atomicWrite`（临时文件 + rename）**、**`withinRoot` 路径复核**、**`readMemory`/`readProgress` 的逐字段白名单重建**：实现正确。

   故合并删除（规则数保持 14：13 + 新增 `external-resource`）。

### 3.2 与复审建议的差异

1. **N2 选建议 ①（增量标题表）而非 ②（索引新鲜才查）**：后者会让同名提示在"先建卡、后检索"的会话里基本失效。
   实现为 `titleHints`（索引重建时填充，`create`/`replace`/`rename` 后增量维护），代价是进程内首次调用若从未建立索引则提示缺席（提示不是门禁）。
2. **N6 两种手段都做**（复审列为二选一）：`config.maxWalkFiles` 可调 **且** 超限改为截断 + `⚠` 上报——"能自救"与"能用"是两个独立需求。
3. **N12 只下移"压空格"，未在定义渲染处额外压缩**：定义里的连续空格同样属于合法输入，静默改写与"用户定稿格式"的承诺冲突。
4. **N3 的重扫覆盖到 `moc`**：复审只点名 `search`/`get`/`update`/`rename`，但 `moc` 的"缺失引用"是同一类误判。

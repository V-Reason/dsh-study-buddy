# 经验复盘：vault 笔记按主题分子文件夹时，领域映射与预生成 ID 的两处坑

- 日期：2026-08-23
- 影响版本：dsh-study-buddy（领域映射 `domainFolders` 位于 preset 配置 `agent.cordis.yml`；`card_id` 预生成 ID 与 `card_create` 实际落盘 ID 可能不一致）
- 场景：用户要求把 `游戏开发/图形学/` 下 83 个笔记按主题分类到 8 个子文件夹；同时保证后续 `card_create` 仍能正确落盘
- 结论：**纯文件移动（Move-Item）本身零风险，真正要处理的是"分类后的目录结构如何与插件的领域→目录映射保持一致"**，以及归档流水线里"先 card_id 生成 ID 再在卡内容里引用"的时序陷阱

## 摘要

Obsidian vault 里知识卡片积累到 80+ 张后平铺在一层目录里，用户要求按主题归档。任务看似是纯文件操作，但实际踩到两处与插件契约相关的坑：

1. **领域映射写死在 preset 配置里**：`card_create` 的落盘位置由 `domainFolders` 决定（`图形学 → 游戏开发/图形学`）。如果只移动文件而不更新映射，新卡会继续落进根目录，归档结构很快被新卡重新打乱——"整理一次，退化三次"。
2. **`card_id` 预生成 ID ≠ `card_create` 实际 ID**：归档流水线里先 `card_id`（预生成 3 个 ID）再 `card_create`（期望用上预生成 ID），但实际 `card_create` 自动生成了**另一组** ID（f7c2/eb26/262b vs 预生成的 4040/2405/699a），卡正文里对"本次关联卡片"的 ID 引用全部写错，事后需要逐个读文件、edit 修正、清理重复行。

## 现象

1. 移动文件后 `card_search`/`card_get` 完全不受影响——两者按内容/ID 检索，与路径无关。**移动文件本身不是坑。**
2. 坑在"往后写"：如果不动映射，下次 `card_create(domain=图形学)` 又落根目录，与子文件夹并存，依旧混乱。
3. 卡正文里"关联卡片"一节引用了预生成的 ID（`202608230733_4040` 等），实际落盘 ID 是 `202608230734_f7c2` 等——`card_get` 按引用查不到，或查到错误目标。

## 根因链

### 坑 1：领域映射是配置，不是约定

- `card-format` 技能文档说"领域→目录映射（图形学 → 游戏开发/图形学 等，见 preset 配置）"——**映射实际位于 `C:\Users\V.Reason\.dsh\.agent-presets\study\agent.cordis.yml` 的 `domainFolders`**，不在插件仓库里，也不在任何 vault 内文件里。
- 查找过程有迷惑性：`mini-study.yml`（profile 目录内）只有 `domainFolders: {}`（空），`cordis.yml` 是空数组，`cordis.patch.yml` 是空数组——真正的配置在 agent preset 的 `agent.cordis.yml`，路径藏在 `preset.yml` → `agent.cordis.yml` 的引用关系里。
- `domainFolders` 的键是**领域键**（card_create 的 `domain` 参数），值才是目录。所以"分类到子文件夹"必须同时给每个子文件夹一个**新领域键**（如 `图形学-后处理 → 游戏开发/图形学/后处理与图像`），否则新卡无法落到子目录。

### 坑 2：card_id 是"占位工具"，card_create 自己生成 ID

- `card_id` 工具描述："生成卡片 ID（YYYYMMDDHHmm_随机4位）"——用途是**预生成占位符**，供对话里提前引用。
- `card_create` 的返回显示"已写入：游戏开发/图形学/….md"时实际自带了生成逻辑，且**不会使用预生成的 ID**（实测：预生成 3 个 ID 全部被忽略）。
- 结果：卡正文里"关联卡片"写 `本次 202608230733_699a`，实际是 `202608230734_eb26`。
- 二次修复时还踩到小坑：`card_link` 工具会在两卡尾部**自动追加**关联行（"- 后续：xxx（ID）"），与手工写的"关联卡片"小节重复——需要读文件后 edit 清理重复行，且 edit 前必须先 read（工具策略要求）。

## 关键证据

1. `card_create` 返回 `已写入：游戏开发/图形学/边缘检测算子…`（ID：202608230734_f7c2），而对话中预生成的是 4040——不一致直接可见。
2. `agent.cordis.yml`（208 行）第 157 行起才是 `domainFolders`；`mini-study.yml` 的 `domainFolders: {}` 是误导性空副本。

## 解决方案（本次采用的）

### 目录迁移

- 8 个子目录：数学与变换 / 渲染管线 / 光照模型 / 纹理与采样 / 后处理与图像 / 动画与特效 / Shader与URP / 光线追踪。
- 移动用 PowerShell `Move-Item -LiteralPath`（文件名含 `×`、`：`、`（）` 等全角字符，`-LiteralPath` 防通配符误解析）。
- 留根目录：`大纲.md`；`_归档/`：旧章节笔记 + GAMES101 注释 + 验证文件（14 个）。
- 文件总数核对：移动 83 + 根留 1 + 归档 14 = 98 个 md，无丢失。

### 映射同步（必须且共 12 键）

在 `agent.cordis.yml` 的 `domainFolders` 里为每个子文件夹加一对"子域键 → 子目录"：

```yaml
图形学-数学与变换: 游戏开发/图形学/数学与变换
图形学-渲染管线: 游戏开发/图形学/渲染管线
图形学-光照模型: 游戏开发/图形学/光照模型
图形学-纹理与采样: 游戏开发/图形学/纹理与采样
图形学-后处理: 游戏开发/图形学/后处理与图像
图形学-动画特效: 游戏开发/图形学/动画与特效
图形学-Shader: 游戏开发/图形学/Shader与URP
图形学-光线追踪: 游戏开发/图形学/光线追踪
```

- 保留原键（`图形学 → 游戏开发/图形学`）作为默认落点/兜底。
- 同步用 `study_memory(set prefs.图形学子目录=…)` 把新约定写进跨会话记忆，否则下个会话 Agent 不知道子域键的存在，仍会传 `图形学` 落根目录。

## 教训清单

1. **整理 vault ≠ 移动文件**。整理是"目录结构 + 映射配置 + 跨会话记忆"三件事；只做移动，下次写卡立刻回退。
2. **domainFolders 的真实位置在 preset 配置**，不在技能文档里。改配置前先全局 grep `domainFolders`，别被 `mini-study.yml` 的空副本误导。
3. **不要在卡正文里引用 `card_id` 预生成的 ID 作为"本次"关联**。正确姿势：先 `card_create`，拿返回的**实际 ID**，再用 `card_link` 或写正文；或干脆等 create 完再补正文。
4. **`card_link` 会自动在卡片尾部追加关联行**，与手写的"关联卡片"小节会重复。要么全用 `card_link`（正文只写概念名不写 ID），要么全手写（正文写完再统一 link），不要混用。
5. **edit 前先 read**（工具策略强制），尤其对"刚被 card_link 更新过"的文件——它可能已追加了行，你的 old_string 会匹配到旧位置或失败。
6. **`.dsh` 用户目录在工作区沙箱外**：改 preset 配置需要 `danger-full-access` 一次性升级，先说明理由再提交，用户可见。
7. **验证要闭环**：移动后至少跑一次 `card_search`（按内容）和 `card_get`（按 ID）确认工具没断；`card_get` 返回的路径字段会显示新位置——这是最直接的证据。

## 后续改进建议

- `card_create` 支持"用指定 ID 落盘"（可选参数 `id`），或至少返回"实际 ID"供后续引用——消除预生成/实际的时序不一致。
- `card_link` 追加行与手写节合并时，考虑去重（同目标卡片不重复追加）。
- provider 的 `domainFolders` 文档化到技能里：给一份"如何加子域键"的单行示例，避免每次排查。

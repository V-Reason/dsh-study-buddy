**第 3 部分亮点**（这几条最能说明"规划—落盘"的记账是可信的）：

- 提案只在对话里：`note_list` 看不到任何新文件。
- 缺微目录会提醒：`⚠ 该目录还没有微目录：请调用 note_toc({ dir: "…" })`。
- 微目录幂等 + 手写导读保留：`note_toc` 连跑两次生成段一致，`<!-- note_toc:begin -->` 之前的导读段原样保留。
- `note_overview` 按「资料 → 章 → 节」聚合：`《验证资料》第1章 验证——3 篇（节：1.1、1.2、1.3）`，并给出「⚠ 节号跳号：1.1 → 1.3」，且不虚构章节。

**第 5 部分亮点**：`note_link` 两侧分别写 `- 后续：[[…]]` 与 `- 前置：[[…]]`，重复调用返回「无改动」；`note_rename` 的 dryRun 给出文件名变更 + 入链清单 + 断链检测，正式改名后 frontmatter 标题、文件名、库内 wikilink 三处同步。

## 三、问题清单（✘ 与 ⚠）

### 3.1 ✘ 归档链路不可用：`note_plan` 没有确认入口（P0）

**现象**：规划提案拿到 `planId` 后，任何 `note_write` 都被拒——

```
写入被门禁拒绝：规划尚未确认（planId：202609152245_0d89b0）
——请让用户拍板后用 note_plan(action=confirm) 确认
```

**根因（源码级）**：

| 位置 | 事实 |
| :-- | :-- |
| [`src/planstore.ts`](../../src/planstore.ts) `buildPlanRecord` | 建记录时写死 `confirmed: false`，注释说「由调用方在用户拍板后置位」 |
| [`src/index.ts`](../../src/index.ts) `notePlan` | 只实现 `create` / `abandon`，**没有 `confirm` 分支**（第 960 行：`note_plan 未知 action "…"（可用 create / abandon）`） |
| 全仓库 | 没有任何把 `confirmed` 置为 `true` 的调用点；报错文案里的 `note_plan(action=confirm)` 是一条**不存在的逃生口** |
| [`src/gate.ts`](../../src/gate.ts) `checkPlan` | `if (!record.confirmed)` 直接 block |
| [`src/planstore.ts`](../../src/planstore.ts) `consumePlanItem` | 第二道同样的校验，`reason: '规划尚未确认；请让用户拍板后重新提交'` |

**后果**：`note_write` 在任何会话、任何 vault 上都必然失败（两道校验先后拦下）。
本次检查为了跑完第 3–5 部分，是在**用户明确授权**下手工把 `.study/plans/<planId>.json` 的
`confirmed` 改成 `true` 才继续的——即"归档链路"目前靠人肉补贴才能工作。

**测试为什么没抓到**：`tests/gate.spec.ts`（第 88 行）与 `tests/noteflow.spec.ts`（第 65 行）
在拿到提案后**直接手改 JSON 置位** `confirmed = true` 再写盘，绕过了缺失的那一步。
所以 `pnpm run check` 全绿与"用户点不出一个已确认的规划"可以同时成立。

**建议**：

1. `notePlan` 增加 `action: 'confirm'`：按 `planId` 覆盖写同一条记录并置 `confirmed: true` / `confirmedAt`，
   同时在 `tools.ts` 的 schema 里加进 enum（现描述已写「规划提案与确认」）。
2. 或者退一步：`note_plan` 出提案后**同一次调用**即视为确认（提案即是"用户看到的那份"），
   把 `confirmed` 初始值改为 `true`——但这会削弱"必须显式拍板"的语义，二选一需拍板。
3. 补一条端到端测试：`notePlan(create) → notePlan(confirm) → noteWrite`，删掉测试里手改 JSON 的写法。

### 3.2 ✘ 第 12 项：门禁检查顺序与清单描述不一致

清单期望「未读期望 → 直接 `note_write`」报「未读取笔记期望」。实测报的是
「本次会话没有已确认的文件夹规划」。根因是 [`src/gate.ts`](../../src/gate.ts) 的 `checkWrite`
按「期望 → 规划 → 路径」**短路**，一次只说一个问题；本会话已读过期望，于是规划那条先返回。

**这是清单文案问题，不是代码缺陷**（短路设计本身是合理的，比一次性抛三条更利于自我纠正）。
两个改法二选一：

- 把第 12 项改成「任一门禁拒绝即可，不必匹配具体文案」；
- 或把该场景改成**新会话里先不读期望**，才能单独触发期望那条。

### 3.3 ⚠ 简介与正文首句重复

正文以 `> ` 引用块开头时（正是《笔记期望.md》要求的"术语首现给定义"写法），
该引用块被**同时**写进 frontmatter 的 `简介:` 字段与正文首行，读起来同一句话连着出现两遍。
本次 4 篇验证笔记全部复现。关联：`简介` 缺省时会从正文首个引用块提取（`note_write` 的 summary 回退逻辑），
提取后没有把正文那行去掉。

### 3.4 ⚠ 批量体检仍打印均分

`note_lint({ scope: 'vault' })` 输出含「平均问题数：0.6 条」，
与清单第 37 项「无均分」、以及技能里「不给分数」的口径冲突。
单篇报告没问题——是「问题清单 + 级别」，没有总分。

### 3.5 ⚠ 小项

| 问题 | 说明 |
| :-- | :-- |
| 微目录标题 | 目录名为 `【验证】/第1章` 时，标题渲染成「第1章」（取末段）；作为导航入口可读，但与规划里的写法不一致，属观感问题 |
| 清单参数名 | 第 34/35 项的 `note_rename({ newTitle })` 实际参数名是 `title`，照抄会报「newTitle 不能为空」 |
| 清单工具名 | 第 29 项写成 `note_update({ action: 'restore' })`，实际 `note_restore` 是独立工具（`note_update` 只接受 append/replace/move/definition） |
| 消费记账未单独触发 | 第 20 项「同标题写第二次」实测报的是 `目标已存在：…`（路径存在性检查先命中），清单期望的「该块已在本规划中写入过」在 [`src/planstore.ts`](../../src/planstore.ts) 里确实存在，但为了不覆盖文件没继续构造；若要精确验，应把同标题写到**规划内的另一个路径** |

## 1. 当前不变量

- 工具面固定为 20 个 `note_*` / `study_*`；课程编译新增独立 `study_course`，其余能力优先扩展现有 action 或字段。
- 笔记写入必须经过“读期望、确认规划、路径在规划内”三道门禁，拒绝时磁盘零改动。
- 替换正文前先存档；`note_update(replace)` 同时保留旧「关联」小节与完整领域标签。
- 期望文件已读状态只按正文哈希判断；权限、复制、改名等元数据变化不能让已读失效。
- Mermaid 与 JSDOM 必须内联进 `lib/index.js`，不得在运行时解析第三方包。
- 发布产物必须带版本和内联标记；`note_library(check)` 与启动日志都要能指出实际运行版本。
- 默认不改真实 vault。自动化回归使用临时目录；真实会话验证优先用 `dryRun`。

## 3. 发布链路

### 3.1 发布前

1. 从 `main` 或已发布的修复分支建立 `codex/<version>-release`。
2. 先写失败测试，再修实现；不要用改断言迁就错误行为。
3. 代码与文档到位后才改版本号，避免过早触发依赖状态刷新。
4. 同时更新 `package.json`、`dsh.plugin.json`、现行文档基线、更新记录和构建产物。

### 3.2 必须通过的检查

```powershell
pnpm run typecheck
pnpm run test
pnpm run build
pnpm run verify:contract
pnpm run verify:deploy -- -Profile desktop
```

- `test` 中的 `tests/build.spec.ts` 会在隔离环境执行真实 Mermaid，并拒绝外部包解析。
- `verify:contract` 检查声明式 bundle、peer 范围、19 工具和平台接线。
- `verify:deploy` 检查仓库版本 ↔ profile 版本 ↔ 产物哈希 ↔ 内联标记 ↔ 预设 ↔ vault。

### 3.3 发布与部署

1. 合并发布分支到 `main`，在 `main` 的同一提交创建附注标签 `vX.Y.Z`。
2. 推送 `main` 和标签。
3. profile 使用 `github:V-Reason/dsh-study-buddy` 时，锁文件会固定到具体提交；
   发布后在 profile 执行 `pnpm update dsh-study-buddy`，不能只重启 DSH。
4. 重启 DSH，确认启动日志出现相同版本和内联标记。
5. 跑 `verify:deploy`，部署五要素必须全绿。

## 6. 故障定位顺序

1. `pnpm run verify:deploy -- -Profile desktop`：先判断是否跑错副本。
2. `note_library(check)`：看实际插件版本和内联标记。
3. `pnpm run verify:contract`：判断 bundle/peer/宿主契约是否失效。
4. `pnpm run test`：判断仓库自身逻辑是否回归。
5. 上述都绿才继续查 DSH 平台升级与宿主 loader 行为。

常见判据：

| 现象 | 优先结论 |
| :-- | :-- |
| 版本号低于仓库或哈希不同 | profile 锁文件仍指向旧提交，执行 `pnpm update dsh-study-buddy` |
| 版本一致但无内联标记 | 构建产物异常，检查 `build.mjs` 与 `tests/build.spec.ts` |
| 含 Mermaid 工具调用抛 `createRequire.resolve.paths` | 运行副本仍是外部 Mermaid 旧构建 |
| 预设与 19 工具整体消失 | bundle 未选中或 peer 不兼容，先看启动 stderr |
| 写入被拒但笔记未变 | 先看门禁原因，不要绕过；拒绝时磁盘零改动是预期 |

## 7. 归档规则

- 已完成的重构需求、选型和实施计划进 `archive/refactor/`。
- 带日期的真机报告进 `archive/reports/`，保持时间点结论，只修失效链接。
- 完整缺陷调查进 `archive/defects/`，现行只保留状态与回归入口。
- 长篇过程实录进 `archive/dev-experience/`，可复用规则提炼回本文。
- 归档不是删除；不把历史快照重新登记为现行执行依据。

# 开发经验总结：四需求落地（一次会话实录）

> 背景：在 dsh-study-buddy 上一次会话中连续落地 4 个需求——①自迭代记忆开关 ②强制开场先读记忆 ③课件 PDF/PPT/DOCX 图片提取 ④阶梯式解剖式笔记模式。测试从 96 项增至 116 项，`pnpm run check`（typecheck + vitest + esbuild）全绿。本文只谈**过程方法论**：哪些环节浪费了 token/时间，哪些做法值得后续项目复用。

## 一、踩过的坑（浪费点）

### 1. 编辑导入行时误删符号（token 级浪费）
在 `src/index.ts` 追加 `opener.ts` 导入时，用一次 `edit` 把多符号导入行整行替换，结果**丢了 `AUTO_PREFS_KEY`**，靠 typecheck 才发现。
- **教训**：一个 `old_string` 里含多个符号时，替换前先数清楚；复杂导入行宁可"整行 delete + 整行 write"，也不要在旧串上改。
- **止损技巧**：改完立即跑 `tsc --noEmit`（本仓库 `pnpm run check` 第一步，秒级）——这条循环本次只付出一轮。

### 2. 测试断言与实现文案耦合，误报（一次来回）
`not.toContain('阶梯式解剖')` 失败——警告文案本身是"阶梯式解剖**模板必需**"，包含该子串。
- **教训**：断言用**带引号的精确子串**（`"### 阶梯式解剖"`）或结构化匹配，别用宽泛词；断言失败先读实际输出，**改断言而不是改实现迁就断言**。

### 3. 未预读受影响测试就改校验（潜在一轮）
计划 4（validateCard 加"缺小节警告"）看似独立，但 `tests/card.spec.ts` 的 `validateCard(base).warnings).toEqual([])` 与 6 个共享 `base` fixture 的用例会**全部**被波及。
- **教训**：任何"新增校验/变更默认行为"前，先 `grep` 该函数的所有既有断言与共享 fixture；改动面预估 = 实现 + 全部受影响测试。

### 4. 宿主机制摸查：看实现文件还是声明文件（多花 3~4 轮）
查 `agent/pre-step` 载荷时先 grep 实现文件（`agent.ts`），以为载荷不含 `agent`；实际完整契约在**声明文件**（`runtime-types.ts`：`{ agent, messages, turn, step, signal }`）。来回一轮才定论。
- **教训**：**契约看声明/类型/测试，实现文件只用来对拍**。DSH 这类大型仓库，事件签名/服务接口优先读 `*.d.ts` 或 runtime-types/服务 `Config` 定义。

### 5. 作用域事件可达性，差点"上线验证"（约 3 轮验证）
预设（standing scope）插件能否收到 agent 作用域分发的 `agent/pre-step`，起初只敢说是"应可达"；最终靠 DSH 自带测试 `scope.spec.ts`（"ancestor-tagged listener admits descendant dispatch，events flow up"）一句话定论。
- **教训**：跨作用域/生命周期问题**先查库内测试**——仓库测试即权威文档，结论可靠且零成本；"可能行"不能写进方案，必须变成"已验证"。

### 6. 单文件大改：多次小 edit vs 一次 write（时间差一个量级）
`file-reading` SKILL.md 改动超过 30%，若用 8 次定点 edit 容易失手且轮次多；整文件 `write` 一次完成（前提：已完整读过原文件）。
- **教训**：改动占比 >30% 用 write 全稿重写；<30% 才用 edit。write 前必须完整 read（默认策略已强制）。

### 7. 命令模板等到部署后再试（风险前置滞后）
PDF/PPTX/DOCX 提取命令是长 Python 模板，若直接提交，语法/库差异会在**部署后**才暴露。本次在本地**自造含图样本**（fitz 生成 PDF、python-pptx 生成 PPTX、zipfile 手拼 DOCX）当场跑通，还顺带验证了无图文件返回 0、中文+空格路径两个边界。
- **教训**：可本地验证的模板/脚本，**先造最小样本跑通再提交**；边界用例（空、异常输入、非 ASCII 路径）必测其一。

### 8. 文档"最后一公里"漏检索（易残留旧文案）
模板从"自由小节"改为"阶梯式解剖"、技能数 5→6 后，若不全局 grep 旧关键词，README/用户指南会残留旧描述。
- **教训**：全局文档替换后必做**残留关键词 grep**（本次 grep「自由小节/5 个技能/自动读回记忆与进度」一次清干净）。

### 9. 方案阶段的"开放不确定点"拖慢整体节奏
计划 2 里"pre-step 是否可达"作为开放问题写进方案，实现前又花了几轮验证。若在**出方案前**先把可行性确认（步骤 4、5 合并到探索阶段），方案直接写"已验证"。
- **教训**：关键机制不确定点**前置到探索阶段**解决；方案文档只列已证实事实，未证实项单独标为"风险与回退"。

### 10. 局部先行 vs 一次全量（正向经验，值得保持）
本次每完成一个模块立即 `npx vitest run <指定文件>`（秒级），全部完成才 `pnpm run check`。没有一次出现"最后爆一片红再从头定位"。
- **教训**：写-测-修的短循环 > "写完一起测"。这条本身是**正向**，作为强制纪律固定下来。

## 二、值得推崇的技巧（后续项目直接复用）

### T1. 纯逻辑模块 + 特性探测接线（本次收益最大）
`opener.ts`（门禁纯函数）与 `memory.ts` 校验函数全部无宿主依赖、可单测；宿主侧接线用 `ctx.get('systemPrompt')` / `ctx.on` **特性探测**包裹，缺服务静默跳过——工具注册永远不被旁路能力拖死（fail-loud 只留给真正错误；这是本仓库历史教训的延续，见 postmortem-2026-08-21）。
- **复用**：任何"增强功能"先写纯函数模块（输入/输出/判定规则显式化），接线层薄而防御。

### T2. 用测试钉住"未来会被精简掉"的内容
`skills.spec.ts` 用关键词断言钉住 file-reading 的图片提取（`get_image_info`/`PICTURE`/`word/media`）、card-format 的五小节、memory-auto 的自迭代要点。未来有人"精简"技能时测试立刻红。
- **复用**：文档/提示词类资产的回归保护 = 关键词钉住测试（成本≈0，收益持续）。

### T3. 决策点显式写成"假设"，方案一次过审
四个方案里把"默认 off / 五小节 warning 级 / 图片上限 12 张 / 不加宿主修改"全部写成显式假设，用户一次确认，没有来回问答。
- **复用**：方案末尾固定"假设"节；开放决策项要么在方案里给默认值+一行替代说明，要么在方案前问清（一次问完）。

### T4. 强制分层：确定性层 + 行为层 + 校验层
需求 3 是典型：插件注入（`system-prompt` 段 + `agent/pre-step` 提醒，确定性强）→ persona 硬门禁（行为强约束）→ 技能细则（可执行规则）。单层失效有下层兜底，且每层都可独立验证。
- **复用**：需要"必须发生"的行为不要只写提示词；画"哪一层能确定性保证、哪一层靠模型遵循、哪一层只做校验提示"。

### T5. 自造样本做命令模板验收
提取脚本类交付物，用脚本生成最小真实样本（含图/无图/中文名字/空格路径四类）本地全过再提交；临时样本不入库，验证完即删。
- **复用**：任何"agent 要执行的命令模板"都必须附一个可复跑的验证步骤。

### T6. 改动前"读受影响测试 + grep 引用"，改动后"局部测试 + 残留 grep"
双向闭环：动代码前先看谁在测它，动文案后查谁在引用它。本次两处翻车（坑 2、3）都是只做了后一半。
- **复用**：作为提交前 checklist 写进流程，而不是靠记忆。

### T7. 一次消息并行多个只读调用 + 先 grep 再 read
探索阶段"glob 目录树 + 多文件 read + grep 关键词"放同一轮并行发起；大文件先 grep 定位段再 read 精确区间，避免整文件占上下文。
- **复用**：上下文预算是稀缺资源；只读调查全部并行，串行只留给写操作。

## 三、一句话总结

本次可避免的浪费集中在**契约/断言的"想当然"**（坑 2、3、4、5——约可省 3~5 轮往返），其余探索类工作都是必要投入。**最值钱的纪律**是：契约先查声明与测试、改动先看受影响断言、模板先跑样本、文档后手做残留 grep、每模块局部测试收口——五条全部零成本，却决定了"一次过"还是"来回修"。
